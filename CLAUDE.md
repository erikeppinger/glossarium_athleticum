# Training App

A local-first, privacy-focused training/workout organization app. Cross-platform (Android → iOS → Windows) via Flutter, built and validated on Android first per the phased plan below.

**Status:** Phase 5 (multi-device sync) complete, plus five follow-up rounds of user-requested additions layered on top (not a numbered phase - see `docs/TODO.md` for the backlog these came from). Phase 5 built conflict detection entirely on Phase 4's file-sharing transport (see the note at the top of Phase 5 in `docs/development-plan.md`): importing a plan JSON that shares an `id` with a local plan but has a different `updated_at` shows a `PlanConflictScreen` (keep local / use incoming / keep both) instead of silently overwriting; "use incoming" preserves logged history for sessions that survive in the incoming version. **Four more real reports, a later session (2026-09-04)**: (1) numeric-only fields across the app (`execution_screen.dart`'s Reps/Weight/RPE, `body_measurements_screen.dart`, `add_exercise_to_plan_screen.dart`, `edit_session_screen.dart`, `calendar_screen.dart`) only set `keyboardType`, which merely picks which on-screen keyboard shows - a physical/emulator keyboard could type arbitrary text (letters, multiple decimal points) straight into a field that later gets blindly `int.tryParse`/`double.tryParse`d, and a bad value would silently vanish rather than error. Fixed by generalizing that same pattern: a new `_InProgressSession` class holds all of it, kept alive in a plain (non-autoDispose) `Provider.family<_InProgressSession, int>` keyed by `planSessionId` - a plain `Provider`, not a `StateNotifier`, is enough since only `ExecutionScreen` itself ever reads/writes this state (`setState()` still drives its own rebuilds against the externally-owned mutable object). The discard dialog gained a real third choice (`_LeaveChoice.leave`) that pops without disposing the session; "Discard" and a successful "Finish session" are the only two paths that call `_session.disposeAll()` (frees the forms' `TextEditingController`s) and invalidate the provider. `TextEditingController` ownership moving from `State.dispose()` (removed entirely) to this explicit end-of-session disposal was the trickiest piece, since `_LoggedSetForm` had never before needed to outlive its owning widget. Regression coverage (`execution_screen_leave_and_resume_test.dart`) verified via stash/pop to genuinely fail against the pre-fix code for the new "Leave" choice specifically (the pre-existing "Discard"/"Keep training" behavior correctly still passed against old code, since those flows weren't broken) - and hit a real test-authoring gotcha worth remembering: the very first logged weight for an exercise is always a personal record (`isPersonalRecord` against empty prior history), so `_SetRow` shows an `Icons.emoji_events` trophy instead of `Icons.check_circle` for it - assert on the shared `'Undo - edit this set again'` tooltip (present for both icons) rather than a specific "logged" icon, or a test asserting `Icons.check_circle` will intermittently fail depending on whether the logged set happens to be a PR.

## Where things are

Columns: `Exercise ID, Exercise Name, Category, Movement Pattern, Muscle Group(s), Equipment, Difficulty, Measurement Type, Description / Cues, Safety Notes, Video Reference`. The `.xlsx` has a "Legend" tab explaining each column — note its column set is the exercise-library schema, distinct from (but related to) the plan-template schema in `templates/`. `Measurement Type` matters: several exercises are scored by distance/time rather than weight×reps, which should drive which input fields the session-logging screen shows for a given exercise.

- `lib/data/app_database.dart` — the Drift `AppDatabase` (`exercises`, `plans`, `plan_sessions`, `plan_session_dates`, `plan_exercises` tables, defined in `lib/data/tables/`). Opened via `package:drift_flutter`'s `driftDatabase()` helper, exposed to the widget tree via `appDatabaseProvider` (Riverpod) in `lib/data/app_database_provider.dart`. DAOs live in `lib/data/daos/` (`ExerciseDao`, `PlanDao` — the latter also defines plain-Dart input/result types like `PlanSessionInput`, `PlanDetails`, `ScheduledSession` since Drift only generates row classes for `@DriftDatabase` tables, not hand-written accessor types — import `lib/data/daos/plan_dao.dart` directly to use them, `app_database.dart` doesn't re-export them).

Called once at app startup (see `main.dart`'s `_startupProvider`) — safe to call repeatedly since it upserts by id.

## Conventions

- State management: **Riverpod** (`flutter_riverpod`). Providers live alongside the feature they back; the DB provider is in `lib/data/app_database_provider.dart`.
- Local DB: **Drift** (SQLite), via `drift` + `drift_flutter` (not `sqlite3_flutter_libs` directly — that package is end-of-life and `drift_flutter`'s `driftDatabase()` handles native setup). Run `dart run build_runner build --delete-conflicting-outputs` after changing any `@DriftDatabase`/table definitions to regenerate `*.g.dart`. Generated `**/*.g.dart` files are excluded from `flutter analyze` in `analysis_options.yaml`.
- Plan/backup file format: versioned JSON (`schema_version` field), defined in `schema/*.schema.json` — kept convertible with the spreadsheet template in `templates/`.
- Test commands: `flutter analyze`, `flutter test`. Full env needed for anything Android-related (see below) — `flutter analyze`/`flutter test` alone don't need it.
- DAO unit tests use `AppDatabase.forTesting(NativeDatabase.memory())` (see `test/data/*_dao_test.dart`) — fast, no platform channels needed.
- **Widget tests with a live Drift `AppDatabase`**: don't build the full app if you can avoid it. A `StreamProvider` watching a Drift `.watch()` query (e.g. `plansListProvider`) that's still mounted when the widget tree is torn down at test end schedules a stream-cleanup timer that fires *after* `flutter_test`'s "no pending timers" check already ran, failing the test with `A Timer is still pending`. `test/widget_test.dart` avoids this by pumping `ExerciseLibraryScreen` directly (a `FutureProvider`-only screen) instead of the full `HomeScreen`/`IndexedStack` (which keeps `PlanListScreen`'s `StreamProvider` alive on a hidden tab). If a future test genuinely needs the full app or a `StreamProvider`-backed screen, unmount it explicitly before the test ends: `await tester.pumpWidget(const SizedBox.shrink()); await tester.pump(); await db.close();` — in that order.
- **Windows-only flakiness**: if `flutter build`/`flutter test` fails with "Flutter failed to delete file at ...\build\native_assets\windows\sqlite3.dll" (a file-lock, likely Windows Defender scanning it right after a process exits), `rm -rf build .dart_tool` and retry — don't chase it as a code bug.
- Package API notes for versions pinned as of Phase 1 (check before assuming an older API from memory/docs): `csv: ^8.0.0` uses `Csv(lineDelimiter: ...).decode(text)`, not the old `CsvToListConverter`. `file_picker: ^12.1.1` uses static `FilePicker.pickFile(...)`/`pickFiles(...)` (no `.platform` getter) and `PlatformFile.readAsBytes()` (the `withData`/`.bytes` pattern from older versions is deprecated).
- **Timers that must survive backgrounding** (Phase 2's rest timer, and anything similar later): never count down tick-by-tick. Store a fixed `DateTime` end point and always recompute `remaining = endTime.difference(now)` from the current wall-clock time - see `lib/logic/rest_timer.dart`. A periodic `Timer` (in `lib/features/execution/rest_timer_controller.dart`) only exists to trigger UI repaints; it isn't the source of truth, so it doesn't matter if ticks are missed/delayed while the app is backgrounded.
- `fl_chart`'s default Y-axis label interval can pick ugly values that overlap (e.g. showing both 70 and 72 when `maxY` is 72) - round `maxY` to a clean multiple of a chosen interval yourself rather than trusting the default (see `history_screen.dart`).
- A `ListTile` with a multi-widget `trailing` (e.g. two buttons in a `Wrap`) can squeeze `title` into a too-narrow column, causing severe character-by-character text wrapping - this actually happened in `plan_import_screen.dart`'s unmatched-exercise card. Prefer a `Column` (title/subtitle on top, an `OverflowBar` of actions below) over `ListTile.trailing` whenever trailing content is more than a single small icon/button.
- **One-shot `FutureProvider`s don't notice direct DB writes from another screen.** `filteredExercisesProvider`/`exerciseCategoriesProvider` (`exercise_library_providers.dart`) are computed once and cached; since `HomeScreen`'s `IndexedStack` keeps every tab mounted from app start, a write that happens on a *different* tab (Settings, Plans import) never triggers a rebuild on the Exercises tab unless something explicitly calls `ref.invalidate(...)` on both providers. This bit three separate call sites before they were all found and fixed by manual testing: `settings_screen.dart`'s delete-all and restore-backup, `plan_import_screen.dart`'s `_createCustom` (spreadsheet import), and `plan_list_screen.dart`'s `_importFromJson`. Any *new* code path that creates/deletes exercises outside the Exercise Library screen itself needs the same two `ref.invalidate` calls - reactive `.watch()`-backed providers (like `plansListProvider`) don't have this problem, only one-shot `FutureProvider`s do.
- **Backup schema note:** `schema/backup.schema.json`'s `sessionLog` requires both `week_number` and `day` alongside `plan_id`/`session_name` - a session name (e.g. "Push Day") can legitimately repeat across weeks in the same plan, so name+plan alone is ambiguous for re-linking a restored log to the correct `PlanSessions` row. See `test/export/backup_roundtrip_test.dart`'s week-disambiguation test.
- Package API note (Phase 3, in addition to Phase 1's csv/file_picker notes): `cryptography: ^2.9.0`'s `Argon2id`/`AesGcm.with256bits()` APIs are used as-is for `lib/security/backup_encryption.dart` - no wrapper needed beyond the envelope format.
- **Real `dart:io` file reads/writes can hang inside a `testWidgets` test on this machine, specifically when the I/O happens *after* `pumpWidget` has run.** Reproduced and isolated during Phase 4 (see `test/features/incoming_share_handler_test.dart`'s file header comment): a plain `File.writeAsString`/`readAsString` call after any `pumpWidget()` in the same test blocked for the full 10-minute test timeout on this Windows setup, every time, regardless of `tearDown` handling - a `testWidgets`/Windows event-loop interaction, not a product bug (a plain `test()` doing the same I/O, e.g. `test/data/local_storage_test.dart`, is unaffected). If a widget-tested code path needs to read/write real files, structure it like `lib/features/sharing/incoming_share_handler.dart`: split a thin `dart:io` wrapper (untested, or tested outside `testWidgets`) from the actual logic, which takes content as a `String`/`bytes` parameter so tests can supply it directly without touching the filesystem.
- Package API note (Phase 4): `receive_sharing_intent` is pinned to `1.8.1`, not `^1.9.0` - 1.9.0 bumped its Android `compileSdk` to 37, which errored on this machine (the auto-installed SDK Platform 37 registered under a non-standard `android-37.0` folder name that Gradle's target resolution couldn't match against the plugin's hardcoded `android-37` requirement - the same class of Android-SDK-tooling unreliability noted below, just triggered via Gradle's own auto-installer this time rather than `sdkmanager` directly). 1.8.1's Dart API (`ReceiveSharingIntent.instance.getInitialMedia()`/`getMediaStream()`/`reset()`, `SharedMediaFile`) is identical to 1.9.0's for what this project uses.
- **Gradle note** (`android/build.gradle.kts`): a `subprojects` block forces every included Gradle module (our own app *and* any plugin) to Java/Kotlin JVM target 17 consistently. Added in Phase 4 because `receive_sharing_intent` 1.8.1's own `build.gradle` sets Kotlin's `jvmTarget` to 17 without updating its Java `compileOptions` to match, which Gradle rejects as "Inconsistent JVM Target Compatibility" - a bug in that plugin's build config, not something fixable from our app's own `build.gradle.kts` alone.
- **This project's SQLite connections don't enforce foreign keys - don't rely on `ON DELETE CASCADE` ever actually firing.** `MaintenanceDao.wipeAllData()` already documented this (deletes children before parents "regardless of whether SQLite's foreign_keys pragma happens to be on"), but `PlanDao.deletePlan()` didn't follow its own doc/test's claim ("cascades to sessions and exercises") until Phase 5 - it only ever deleted the `Plans` row, silently leaving orphaned `PlanSessions`/`PlanExercises` rows behind. The bug went unnoticed because its own test only checked that `getPlanDetails` returned null, which is true the instant the parent row is gone regardless of orphaned children - it never queried a child row directly. Fixed by making `deletePlan()` explicitly delete `PlanExercises` → `PlanSessions` → `Plans` in that order (see `plan_dao.dart`), added `SessionLogDao.deleteLogsForPlanSession()` alongside it for the same reason, and rewrote the test to check a child row is actually gone, not just the parent. **Any new "delete an X" method must delete X's children explicitly, in dependency order** - never assume a table's foreign key `onDelete: KeyAction.cascade` declaration alone deletes anything at runtime here, and don't trust a test that only checks the parent disappeared to prove cascade-like behavior actually happened.
- **The one-shot-`FutureProvider` cache gotcha (see above) isn't limited to the Exercise Library's providers - watch for it on any per-id `FutureProvider.family` too.** `plan_detail_screen.dart`'s `planDetailsProvider(planId)` (moved to `plan_providers.dart` in Phase 5, was private before) doesn't notice a plan's data being rewritten under its own id from elsewhere (Phase 5's sync conflict resolution) unless that code calls `ref.invalidate(planDetailsProvider(id))` too - found via a live, no-app-restart manual re-test (a cold-restart check alone wouldn't have caught it, same lesson as Phase 3's category-chip bug).
- **Any direct mutation to a plan's contents must bump `Plans.updated_at` itself - there's no trigger that does it automatically.** `PlanDao.addSession()`, `addExerciseToSession()`, and `assignSessionDate()` all call a shared `_touchUpdatedAt(planId)` for this reason. Skipping it doesn't break anything locally, but silently breaks Phase 5's sync conflict detection (which compares `updated_at`) for that change - a future edit could get lost in a sync without ever showing a conflict prompt. Any new plan-mutating DAO method needs the same call.
- **A `TextEditingController`-derived UI value (e.g. a submit button's enabled state via a `_canSubmit()` check in `build()`) will not update as the user types unless something explicitly listens for it.** Found in `add_exercise_to_plan_screen.dart`: the "Add to plan" button used `_canSubmit()` in `build()`, but nothing rebuilt the widget when the underlying `TextEditingController`s changed, so the button stayed permanently disabled once the initial (empty-field) build had happened - a real bug, not just a test artifact, caught via a widget test that entered text and then checked the button state. Fixed with a `ListenableBuilder(listenable: Listenable.merge(controllers), ...)` wrapping just the affected widget, rather than a whole-screen `setState()` per keystroke.
- **`DropdownButtonFormField`'s dropdown-menu overlay is fragile to drive from `testWidgets`** (intermittent "would not hit test on the specified widget" warnings when tapping an open menu's items). Prefer the already-proven pattern instead: a plain button/`ListTile` showing the current selection, opening a `showDialog` + `SimpleDialog`/`SimpleDialogOption` list on tap (see `plan_import_screen.dart`'s exercise-matcher dialog, and `add_exercise_to_plan_screen.dart`'s plan/session pickers) - both easier to test and consistent with the rest of the app.
- **A plain `ListView(children: [...])` (not `.builder`) still lazily *mounts* elements per `SliverList` viewport visibility**, even though the `Widget` objects for every child are constructed eagerly. In a `testWidgets` test with more form fields than fit in the default (small) test viewport, widgets below the fold - e.g. a submit button after several conditionally-shown sections push it down - aren't in the `Element` tree at all (not just unpainted) until scrolled into view, so `find` won't see them. Fix: enlarge the test viewport (`tester.view.physicalSize = const Size(w, h); tester.view.devicePixelRatio = 1.0;`, with `addTearDown` to reset both) rather than scripting scroll gestures for every interaction.
- **`add_exercise_to_plan_screen.dart`'s full interactive flow has no widget test** - the multi-dialog form (pick-plan dialog → pick-session dialog → text entry → submit) reproducibly hung the test runner for the full 10-minute timeout partway through, even in a minimal version with no database writes and no file I/O, and even after fixing the two real bugs above. The cause wasn't isolated (unlike the `dart:io`-after-`pumpWidget` hang in Phase 4, which had a clear, reproducible root cause). Coverage for this screen is DAO-level only (`test/data/plan_dao_test.dart`'s `createEmptyPlan`/`addSession`/`addExerciseToSession` tests) plus manual verification on the emulator. If revisiting this, budget time for genuine `flutter test` framework debugging, not just app-code debugging.
- **Material 3's default Android overscroll indicator visually stretches scrollable content** (`StretchingOverscrollIndicator`, the default when `ThemeData.useMaterial3` is true, which it is by default) - pulling past a list's top/bottom scales the whole subtree including its text, which reads as a layout bug rather than a platform default. Fixed app-wide via a custom `ScrollBehavior` (`main.dart`'s `_GlowScrollBehavior`) overriding `buildOverscrollIndicator` to use the classic `GlowingOverscrollIndicator` instead. If a future screen still shows stretching, check it isn't wrapped in its own nested `ScrollConfiguration`.
- **Display-unit settings (kg/lbs, week start) are per-device preferences, not synced plan data** - stored via `shared_preferences` and loaded once at startup (`main.dart`'s `_startupProvider`, alongside the exercise-seed step) into `lib/features/settings/app_preferences.dart`'s `AppPreferencesNotifier` (a `StateNotifierProvider`). Conversion functions live in `lib/logic/units.dart` (kept pure/DB-free, matching the rest of `lib/logic/`). The DB always stores weight in kg regardless of the setting - conversion only happens at input/display boundaries (execution mode's Weight field, the history screen). `lib/logic/progression.dart`'s auto-progression suggestion text is a known gap: it always formats in kg since threading a unit through that pure, heavily-tested logic wasn't worth the risk for a first pass - revisit if it comes up again.
- **Editing a live emulator's SQLite database directly via `adb`** (done once, for the user-supplied V4 exercise cross-reference) is a legitimate but risky last resort for bulk data fixes with no corresponding in-app bulk-edit feature - it bypasses the app's own tested import/DAO paths, so treat it as an exception, not a pattern. If it comes up again: force-stop the app first (`adb shell am force-stop <package>`), pull the DB with `adb exec-out run-as <package> cat <path>` (plain `adb shell ... cat ... > file` corrupts binary output - use `exec-out`), apply changes with the `sqlite3` CLI (already present at `$ANDROID_HOME/platform-tools/sqlite3`) and verify with `PRAGMA foreign_key_check`/`PRAGMA integrity_check` before pushing back, then relaunch. Also remember to bump `plans.updated_at` by hand for any plan-content edit (see the DAO convention above) since no app code runs to do it for you. Git-bash's automatic path conversion mangles any `/data/...`-style absolute path passed to `adb shell`/`adb exec-out`/`adb push`/`adb pull` - set `MSYS_NO_PATHCONV=1` for those commands.
- **Deletion is structural, not all-or-nothing - and logged history is never collateral.** The governing asymmetry: a plan can be re-imported from a spreadsheet in a minute; a record of what was actually lifted last March cannot be recovered by any means. So (a) **archive** (`Plans.archivedAt`, `PlanDao.archivePlan`) is the reversible default for "get this out of my way", and gets an undo snackbar rather than a confirmation dialog - confirming a harmless action only trains users to dismiss dialogs unread; (b) any irreversible delete must first show its blast radius in real counts (`getPlanDeletionImpact` → "12 logged workouts, 148 sets, March–August"), because nobody can consent to a loss they can't see; (c) deleting a parent offers to **keep** dependent history (`deletePlanKeepingHistory` retains trained sessions as detached tombstones, drops untrained ones) - destroying it is a separate explicit choice (`deletePlanAndHistory`); (d) the same applies to exercises (`getExerciseUsage`/`deleteExerciseKeepingHistory`). Any new "delete an X" feature should follow this shape. Semantics are pinned by `test/data/plan_deletion_test.dart`.
- **Features that touch body image are opt-in, and a "no" is remembered.** `BodyTracking` is deliberately tri-state (`notAsked`/`enabled`/`declined`) rather than a bool: weighing yourself isn't a neutral act, so the feature stays hidden until asked for, and someone who declines is never asked again. A dismissed prompt is *not* an answer and leaves the state at `notAsked`. Same reasoning would apply to any future streak/calorie/body-comparison feature.
- **A `TextEditingController` created inline in a `showDialog` caller and disposed right after the returned `Future` resolves races the dialog's own exit transition.** `Navigator.pop()` resolves the `showDialog` future immediately, but the route's exit animation keeps rebuilding the same `builder` for several more frames while it animates out - disposing the controller in that gap threw "A TextEditingController was used after being disposed" (found while adding execution mode's post-session note prompt, `execution_screen.dart`'s `_NotePromptDialog`). Fix: give the dialog's content its own `StatefulWidget` that owns the controller and disposes it in its own `State.dispose()`, which the framework only calls once the route is actually removed - never dispose a dialog-scoped controller manually in the caller.
- **A button whose only visible state change comes after an `await` stays tappable for that whole async gap - a fast double-tap can fire two overlapping handler calls.** Execution mode's set-check button (`_logSet` in `execution_screen.dart`) awaits a DB read (for PR comparison) before its `setState` flips the button to its "logged" icon; nothing disabled the button in between. Suspected (though unreproduced) cause of a user report that checking sets was "still inconsistent." Fixed with a synchronous pending flag flipped *before* the await, checked at the top of the handler to reject a second call and swapped for a disabled/loading visual meanwhile (`_LoggedSetForm.pending`). Any future button whose handler does DB/network work before its own `setState` needs the same guard, not just a "was this event already handled" check inside the async body (which is already too late once two calls have both started).
- **A migration that both adds new columns and changes an existing column's nullability needs `TableMigration`'s `newColumns` list, or the generated COPY statement reads columns that don't exist yet.** Making `SessionLogs.planSessionId` nullable (for ad-hoc activities with no scheduled session) also added `activityName`/`durationSec`/`distance` in the same `schemaVersion` bump. `await m.alterTable(TableMigration(sessionLogs))` alone crashed on an actual upgrade (schema 7→8, caught on-device, not by any test - this project has no automated migration tests, since `AppDatabase.forTesting` always starts fresh via `onCreate` and never exercises `onUpgrade` at all) with `SqliteException: no such column: "activity_name"`: the generated `INSERT INTO tmp_for_copy... SELECT ... FROM session_logs` tried to select the brand-new columns from the *old* table, which obviously doesn't have them. Fix: pass every genuinely-new column explicitly via `TableMigration(sessionLogs, newColumns: [sessionLogs.activityName, ...])`, which tells drift to leave them at their default (null, since nullable) instead of trying to copy them. Any future migration combining "recreate the table" (nullability/type changes) with "add a column" needs this. Because this class of bug only surfaces on a real upgrade path, not a fresh install, it's worth a deliberate on-device upgrade check (open the previous APK's data, install the new one, watch the launch log) whenever `schemaVersion` bumps with more than a plain `addColumn`.
- **A function that takes a wider generic type (`Iterable<num>`) than the concrete collection callers actually pass (`List<double>`) must not call `.reduce()`/`.fold()` with a closure inferred from the wider parameter type.** `lib/logic/progression.dart`'s `isPersonalRecord(num newValue, Iterable<num> priorValues)` did `priorValues.reduce((a, b) => a > b ? a : b)` - the closure's static type, inferred from the declared `Iterable<num>` parameter, is `num Function(num, num)`. That's fine when the caller actually passes something reified as `num`/`int` (every existing unit test used a `[55, 60]` list literal, which infers as `List<num>` and never reproduces this). But `execution_screen.dart`'s real caller builds `List<double> allPrior = [...priorFromDb, ...priorWeights]` from real logged weights - passing that concrete `List<double>` into the `Iterable<num>` parameter doesn't change its runtime reification, and `reduce` dispatches against the *object's actual* type parameter (double), which requires a `double Function(double, double)` combiner. The mismatch throws `TypeError: type '(num, num) => num' is not a subtype of type '(double, double) => double'` - caught live on an emulator: logging a set against 2+ real prior weights threw this from inside the awaited `_logSet`, which fired *before* `form.logged = true` was ever reached, permanently freezing that set's pending spinner with no visible error anywhere (not even in a normal `flutter test` run, since nothing there ever passes a real `List<double>`). Fixed by replacing the `.reduce()` call with a manual max-tracking loop, which only ever does `>` comparisons on `num`s and so can't hit this reification mismatch regardless of what the iterable reifies to. **Any function accepting a supertype-generic `Iterable`/`List` parameter should avoid `.reduce()`/`.fold()`/other generic-callback methods on it - use a manual loop instead** - and cover it with a test that passes a concretely-typed collection (`List<double>.from([...])`, not a bare literal), not just one that happens to reify as the declared parameter type.

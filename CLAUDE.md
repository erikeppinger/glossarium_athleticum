# Training App

A local-first, privacy-focused training/workout organization app built with Flutter. Ships for Android, Windows (`.exe` + MSIX) and Linux; iOS builds unsigned on GitHub Actions only (no Apple account yet). Public repo: github.com/erikeppinger/glossarium_athleticum (the app is being renamed to Glossarium Athleticum). The original phased roadmap is in `docs/development-plan.md`.

**Status:** Phases 1-5 complete; Windows and Linux desktop builds ship alongside Android. Round-by-round development history (bug reports, verification notes, ship logs) is in `docs/dev-history.md` - read it when you need the background on why something was built a particular way; the standing rules from it are under Conventions below.

## Where things are

- `docs/development-plan.md` — the authoritative phased plan (Phase 0 through Phase 8). Background on the original scope and exit criteria; current work is driven by user requests on top of it.
- `templates/` — the user-facing spreadsheet template (`.xlsx` and `.csv`) for authoring a training plan outside the app, per the Phase 1 "spreadsheet import" feature. Both files define the plan schema: one row per exercise-in-a-session, columns `Week, Day, Session Name, Order, Exercise Name, Sets, Reps, Weight/Intensity, Rest (sec), Notes, Video URL, Picture, Embedding, Created By` (the last three optional). The `.xlsx` also has an "Instructions" tab explaining each column and a "Plan" tab with example rows plus dropdown/number validation — use it as the spec for the import parser's expected shape.
- `seed-data/` — 47 sample exercises (`.xlsx` and `.csv`) for seeding and testing the exercise library in Phase 1. Columns: `Exercise ID, Exercise Name, Category, Movement Pattern, Muscle Group(s), Equipment, Difficulty, Measurement Type, Description / Cues, Safety Notes, Video Reference, Embedding, Picture, Author` (the seed loader reads the first 12 positionally). The `.xlsx` has a "Legend" tab explaining each column — note its column set is the exercise-library schema, distinct from (but related to) the plan-template schema in `templates/`. `Measurement Type` matters: several exercises are scored by distance/time rather than weight×reps, which should drive which input fields the session-logging screen shows for a given exercise.
- `schema/` — versioned JSON Schema definitions (`exercise.schema.json`, `plan.schema.json`, `backup.schema.json`) for the plan/backup file format described in Phase 0/3, kept convertible with the `templates/` spreadsheet.
- `lib/data/app_database.dart` — the Drift `AppDatabase` (`exercises`, `plans`, `plan_sessions`, `plan_session_dates`, `plan_exercises` tables, defined in `lib/data/tables/`). Opened via `package:drift_flutter`'s `driftDatabase()` helper, exposed to the widget tree via `appDatabaseProvider` (Riverpod) in `lib/data/app_database_provider.dart`. DAOs live in `lib/data/daos/` (`ExerciseDao`, `PlanDao` — the latter also defines plain-Dart input/result types like `PlanSessionInput`, `PlanDetails`, `ScheduledSession` since Drift only generates row classes for `@DriftDatabase` tables, not hand-written accessor types — import `lib/data/daos/plan_dao.dart` directly to use them, `app_database.dart` doesn't re-export them).
- `lib/data/seed/exercise_seed_loader.dart` — parses the CSV bundled at `assets/seed-data/strongman_exercise_database.csv` (a copy of `seed-data/`, registered in `pubspec.yaml`) and upserts it into the `exercises` table. Called once at app startup (see `main.dart`'s `_startupProvider`) — safe to call repeatedly since it upserts by id.
- `lib/import/plan_spreadsheet_parser.dart` — the plan-template CSV parser (`parsePlanCsv`), exercise-name matcher (`matchExercisesAgainstLibrary`), and week/session grouper (`groupIntoSessions`). Columns are matched by header name, not position, so a reordered template still parses. Per-row problems (missing required value, unparseable number) are collected as `PlanImportRowError`s rather than thrown, so one bad row doesn't block importing the rest of the file; only structural problems (a required column missing entirely, an empty file, or a file over `maxImportRows`) throw `PlanImportFormatException`. Exercise-name matching is exact-after-normalization only (lowercase, apostrophes stripped, punctuation/whitespace collapsed) — deliberately not fuzzy/edit-distance, so it never silently matches the wrong exercise; unmatched rows surface in `PlanImportScreen` for the user to resolve (pick an existing exercise or add a custom one).
- `lib/features/` — one directory per feature (`exercise_library/`, `plans/`, `calendar/`, `execution/`, `history/`), each with its Riverpod providers alongside its screens. `lib/home_screen.dart` ties them together with a bottom `NavigationBar` over an `IndexedStack` (so switching tabs doesn't lose scroll position/state, but also means every tab's providers are alive simultaneously — see the note in `test/widget_test.dart` about why that test targets `ExerciseLibraryScreen` directly instead of the full app).
- `lib/logic/` — pure, DB-free business logic, kept separate from Drift/Flutter so it's trivially unit-testable (per the dev plan's call-out that this is "the one piece of business logic worth heavy edge-case testing"): `progression.dart` (`suggestNextSet` - auto-progression suggestions; `isPersonalRecord` - PR detection, shared by both the history screen and execution mode) and `rest_timer.dart` (pure time math for the rest timer, see Conventions below for why it's split from the Timer/StateNotifier plumbing).
- `lib/data/tables/session_logs_table.dart` + `lib/data/daos/session_log_dao.dart` — `SessionLogs`/`LoggedSets` tables (one execution of a scheduled `PlanSessions` row, with its completed sets) and their DAO. Mirrors `schema/backup.schema.json`'s `sessionLog`/`loggedSet` shape, except it references the specific `PlanSessions` row (`planSessionId`) rather than duplicating `plan_id`+`session_name` as flat fields - Phase 3's JSON export will derive those via a join. Adding these tables was the first schema migration (`schemaVersion` 1 → 2, see `AppDatabase.migration` in `app_database.dart`) - bump the version and add an `onUpgrade` step for any future table changes rather than only relying on `onCreate`.
- `lib/features/execution/execution_screen.dart` — the "execution mode" screen (Phase 2): logs every set for a scheduled session inline (not a multi-step wizard), starts the rest timer after each logged set, computes PR status per set against DB history plus any earlier sets logged in the same in-progress session, and only writes to the DB once ("Finish session") - an interrupted/abandoned session simply logs nothing, which is an accepted simplicity tradeoff for Phase 2.
- `lib/security/backup_encryption.dart` — `encryptBackup()`/`decryptBackup()` (Phase 3): Argon2id key derivation (memory 19456 KiB, 2 iterations, 1 parallelism - OWASP-recommended minimums) feeding AES-256-GCM, wrapped in a versioned self-describing JSON envelope (salt/nonce/mac base64-encoded). `BackupDecryptionException` on any tamper/wrong-passphrase/malformed-envelope case - never throws a raw crypto exception up to the UI.
- `lib/export/plan_export.dart` / `lib/import/plan_json_import.dart` — single-plan export/import (CSV or JSON), independent of the full-backup format. `importPlanJson`'s exercise resolution order: exact id match → normalized-name match (reuses `lib/logic/exercise_name_matching.dart`, shared with the spreadsheet importer) → create a new custom exercise.
- `lib/export/backup_export.dart` / `lib/import/backup_import.dart` — full-device backup/restore (Phase 3). Restore is "wipe then reimport from scratch," not a merge, matching the dev plan's exit criteria. Wipe and reimport run inside one `db.transaction` (`_wipeAndRestore`), so a backup that fails part-way rolls back and leaves the device's data untouched; any such failure surfaces as `BackupJsonFormatException`, which the restore callers already show. Before 2026-10-14 a single damaged entry left the device wiped and half-restored, with no message (`test/import/backup_restore_rollback_test.dart`). Session logs are matched back to their `PlanSessions` row via `PlanDao.findSessionByNaturalKey({planId, weekNumber, day, sessionName})` - see Conventions below for why `week_number`/`day` are required, not just `session_name`.
- `lib/data/daos/maintenance_dao.dart` — `MaintenanceDao.wipeAllData()`: deletes all rows from all 6 tables inside one transaction, in FK-safe order (loggedSets → sessionLogs → planExercises → planSessions → plans → exercises). Used by both "Delete all data" and as the first step of backup restore.
- `lib/features/settings/settings_screen.dart` — Export/Restore/Delete-all UI (Phase 3). See Conventions below for the FutureProvider cache-invalidation gotcha this screen (and the Plans import screens) had to work around.
- `lib/features/settings/backup_dialogs.dart` — `promptPassphrase()`/`confirmDestructiveAction()` (Phase 3, extracted Phase 4): shared dialogs used by the Settings screen's export/restore/delete-all and by Phase 4's incoming-share handler, since both need "confirm this is destructive" and "ask for a passphrase" in the same shape.
- `lib/features/sharing/incoming_share_handler.dart` — Phase 4: routes a plan/backup file received from outside the app (Bluetooth, WhatsApp, "Open with", etc.) into the same import flows used for a manually-picked file. Split into `handleSharedFile` (thin `dart:io` wrapper - reads the file, never unit-tested directly) and `handleSharedContent` (the actual extension-based routing logic, tested with in-memory strings) - see Conventions below for why. Wired into `lib/home_screen.dart`'s `initState`/`dispose` via `package:receive_sharing_intent`.
- `android/app/src/main/AndroidManifest.xml` — Phase 4: added `ACTION_VIEW`/`ACTION_SEND` intent filters so the app can be opened via "Open with" or chosen as a share target - narrowed from an initial `*/*` mimetype to `application/octet-stream`/`application/json`/`text/csv` (2026-09-05, see the Status entry on that date for why); `MainActivity`'s `launchMode` changed from `singleTop` to `singleTask` (recommended by `receive_sharing_intent`, prevents a new Activity instance per incoming share).
- `lib/import/plan_sync.dart` — Phase 5: `checkPlanSync()` (a `PlanSyncNew`/`PlanSyncUpToDate`/`PlanSyncConflict` sealed result, based on comparing a local plan's `updated_at` to an incoming JSON's), `findLogsThatWouldBeLost()` (which local session logs a "use incoming" would delete - callers must warn before acting on this), and `applyIncomingPlan()` (replaces a plan's data under its existing id, re-linking any session logs whose session survives in the incoming version by natural key). Pure DB logic, no widgets - kept testable the same way `lib/logic/` is, just DB-touching instead of DB-free.
- `lib/features/plans/plan_conflict_screen.dart` + `lib/features/plans/plan_sync_handler.dart` — Phase 5 UI: `importOrSyncPlanJson()` is the shared entry point both the manual "Import plan -> From plan file" flow and the incoming-share handler call, so a sync conflict is caught the same way regardless of how the file arrived; it shows `PlanConflictScreen` on a `PlanSyncConflict`.
- `lib/features/exercise_library/exercise_detail_screen.dart` — shows an exercise's full library entry (description, safety notes, muscle groups, reference video via `url_launcher`) with an "Add to plan" button and a "View history" app-bar action. `exercise_library_screen.dart`'s list now taps into this (previously tapped straight into history) and long-presses into a quick-actions bottom sheet (view details / view history / add to plan).
- `lib/features/plans/add_exercise_to_plan_screen.dart` — lets an exercise be added into a new-or-existing plan/session inline, via `PlanDao.createEmptyPlan()`/`addSession()`/`addExerciseToSession()`. Plan/session pickers are tap-a-button-then-`SimpleDialog` (matching `plan_import_screen.dart`'s existing exercise-matcher dialog), not `DropdownButtonFormField` - see Conventions below for why.
- `lib/features/execution/start_session_helper.dart` — `startSessionWithMoveToTodayPrompt()`: shared by the plan detail screen's Start button and the calendar's day-list tap. Prompts to move a session to today (and does so, invalidating both `scheduledSessionsProvider` and `planDetailsProvider(planId)`) only when it has an assigned date that isn't today; otherwise starts immediately.
- `lib/features/execution/rest_timer_overlay.dart` — `RestTimerOverlay`: a floating tap-to-return countdown chip, mounted in `main.dart`'s `MaterialApp.builder` so it floats above every route (hidden while `ExecutionScreen` itself is visible, via `executionScreenVisibleProvider`). Works because `restTimerControllerProvider` isn't autoDispose (see its own doc comment) - state and the 250ms ticker both survive after `ExecutionScreen` (which started the timer) is popped, and the overlay picks up where it left off since it's a different, always-mounted watcher.
- `lib/features/exercise_library/create_exercise_screen.dart` — `CreateExerciseScreen`: the full-schema custom-exercise creation flow (name/category/movement pattern/muscle groups/equipment/difficulty/measurement type/description/safety notes/video/author), with a preview step before saving and a post-save prompt into `add_exercise_to_plan_screen.dart`. Reachable via a "+" action on the Exercise Library app bar - distinct from the bare-name custom exercise creator still used by `plan_import_screen.dart`'s unmatched-exercise resolution (that one deliberately stays minimal, since it's mid-import and the user can enrich the exercise later via this screen).
- `lib/features/notifications/` — scheduled reminders: `notification_service.dart` (a thin `flutter_local_notifications` wrapper, no app logic - besides scheduling/cancelling, it also exposes `onNotificationTap` (a broadcast `Stream<String>` fed by `onDidReceiveNotificationResponse`) and `consumeLaunchPayload()` (for a tap that launched the app cold, via `getNotificationAppLaunchDetails()`)) and `reminder_coordinator.dart` (`resyncReminders()`, which cancels everything and rebuilds the full pending set from current settings + scheduled sessions + per-plan report opt-ins - never diffs, so a rescheduled/deleted session can't leave a stale reminder). Called on app launch (`home_screen.dart`) and after any date assignment (`plan_detail_screen.dart`, `start_session_helper.dart`) or report-preference change (`plan_report_prompt.dart`, `plan_actions.dart`). *What* to schedule lives in `lib/logic/notification_schedule.dart` (pure, unit-tested); every `ScheduledReminder` carries a `payload` string built by `lib/logic/reminder_payload.dart` (also pure/unit-tested), which is the single place both the scheduling side and `home_screen.dart`'s tap-handling side agree on the string format, so tapping a notification actually opens the right screen (`workout:<planSessionId>` pushes `ExecutionScreen`; `digest`/`plan_report:<planId>` switch to the Progress tab). **Android setup this needed:** `POST_NOTIFICATIONS`/exact-alarm/boot permissions and the plugin's two receivers in `AndroidManifest.xml`, plus `isCoreLibraryDesugaringEnabled = true` and a `coreLibraryDesugaring(...)` dependency in `android/app/build.gradle.kts` - the build fails with a bare "requires core library desugaring" AAR-metadata error without the latter.
- `lib/features/plans/plan_report_prompt.dart` — `maybeAskAboutPlanReports()`: asks once, the first time a session in a plan is started (wired into `start_session_helper.dart` right after the existing body-tracking prompt), whether to get a periodic "check your progress on this plan" reminder - same tri-state opt-in shape as `BodyTracking` (see the body-image convention below) but per-plan (`Plans.reportPreference`/`reportFrequencyDays`/`reportOptInAt`, schemaVersion 9), since interest in check-ins varies by plan. `askReportFrequency()` (7/14/30-day `SimpleDialog` picker) is shared with `plan_actions.dart`'s "Progress reminders" entry, which lets the choice be turned on/off/re-cadenced later, since the first-session prompt only ever shows once per plan.
- `lib/features/plans/edit_session_screen.dart` — edits an existing session's exercises (sets/reps/weight/rest/notes, reorder, remove) via `PlanDao.updatePlanExercise`/`deletePlanExercise`/`movePlanExercise`. `deletePlanExercise` renumbers the survivors so `order` stays contiguous - `addExerciseToSession` derives the next order from the current max, so a gap left behind would eventually produce duplicate orders. Its checkbox-selection UI (`_SelectionPurpose`) now serves both "Group into superset" and "Save as block" - copy that enum pattern rather than a plain `bool` for any future third purpose sharing the same selection list.
- `lib/data/tables/blocks_table.dart` / `lib/data/daos/block_dao.dart` / `lib/features/plans/block_edit_screen.dart` — reusable named exercise groups ("blocks", e.g. "Warm-up"). Stamp semantics throughout: `PlanExerciseToBlockInput.toBlockInput()`/`BlockExerciseToPlanInput.toPlanInput()` (`block_dao.dart`) each produce an independent copy, never a live link - inserting a block or editing it afterward never retroactively affects the other. `BlockEditScreen` always mutates in place (no fork) since a block has no logged history of its own to protect. Authored via `edit_session_screen.dart`'s "Save as block" (from an existing session's selected exercises), from scratch via "Manage libraries & blocks"' "+", or inline via either "Insert block" picker's own "Create new block" option (`createBlockFromScratch()` in `block_edit_screen.dart`, shared by both pickers - prompts for a name, creates the block, and opens `BlockEditScreen` immediately, so a block can be authored without leaving the plan/session being built); inserted via "Insert block" in both `edit_session_screen.dart` (forks, like adding a single exercise) and `plan_builder_screen.dart` (still in-memory, no fork needed).
- Any dialog with a `TextField` whose controller is created inline in the calling method and disposed via `showDialog(...).then((result) { controller.dispose(); ... })` has a real, reproducible crash: disposing right after the Future resolves races the dialog's own exit transition, which keeps rebuilding that `TextField` for a few frames while it animates out, throwing "A TextEditingController was used after being disposed." `plate_calculator_screen.dart`'s `_AddPlateDialog` already had the fix (a dedicated `StatefulWidget` owning the controller, disposed in its own `State.dispose()`); `edit_session_screen.dart` had *two* dialogs with the actual bug for a while before anyone wrote a widget test that typed into one (`_promptForkName`, `_promptBlockName` - both since fixed, see `_ForkNamePromptDialog`/`_BlockNamePromptDialog`). Grep for `.then((` immediately after a `showDialog` call with an inline `TextEditingController` above it before adding any new text-prompt dialog.
- `lib/features/progress/` — the Progress tab (one of five bottom-nav destinations; Settings is deliberately *not* one - it's reached via `settingsAppBarAction(context)`, a gear in each tab's app bar, defined in `home_screen.dart`): `progress_screen.dart` (period toggle + prev/next navigation, summary cards, cross-exercise dashboard, plain-text share via `share_plus`, and a PDF export - see below) and `progress_providers.dart` (`periodSummaryProvider.family`/`exerciseProgressDashboardProvider`, both backed by new `SessionLogDao` methods `getPeriodSummary`/`getLatestTopSetPerExercise`). Date-range math lives in `lib/logic/summary_period.dart` (`computeSummaryRange`, pure/unit-tested) rather than the widget, alongside the `WeekStart`/`SummaryPeriod` enums themselves - moved there (not `app_preferences.dart`, which now just imports/re-exports them) to keep `lib/logic/` free of `lib/features/` dependencies, matching `lib/logic/units.dart`'s precedent.
- `lib/export/progress_report_pdf.dart` — `buildProgressReportPdf()`: the Progress tab's "Share/Save as PDF" report (header, summary stats, a hand-rolled volume bar chart, exercise dashboard table) via `package:pdf`. Pure data in, bytes out, no DB/widget-tree dependency - see the Status entry above for the two real bugs (font Unicode coverage, `pw.Table` pagination) found building it.
- Exercise "creator" filtering (Exercise Library screen): `Exercises.sourcePlanName`/`Exercises.author` (nullable, schemaVersion 3) - `sourcePlanName` is a plan-name snapshot set automatically wherever a custom exercise is created during a plan import (`plan_import_screen.dart`, `plan_json_import.dart`); `author` is optional free text on `create_exercise_screen.dart`. `ExerciseDao.search()`'s `creator` param takes `ownExercisesFilter` (custom, no plan/author attribution) or `'plan:<name>'`/`'author:<name>'`; `getCreatorFilterOptions()` enumerates the latter two for the filter-chip row.
- `lib/logic/plate_calculator.dart` / `lib/features/tools/plate_calculator_screen.dart` — greedy largest-plate-first per-side calculator. The actual form is `PlateCalculatorForm` (a plain `Column`, no `Scaffold`/scroll view of its own); `PlateCalculatorScreen` (Exercise Library toolbar) and `showPlateCalculatorSheet()` (a modal sheet, called from `ExecutionScreen`'s app bar mid-session) are both thin hosts around the same form - add a third entry point the same way rather than copying the form's logic.
- `random_workout_screen.dart`'s "create a throwaway single-session plan via `PlanDao.createPlan()`, never surfaced as a real plan" trick is now shared as `startNowWithExercise()` in `lib/features/execution/start_session_helper.dart` - extracted there once a third caller needed it (Today tab's "Start a session"), alongside `exercise_detail_screen.dart`'s own "Start now" button. Copy this pattern (not a new schema concept, and call the shared function rather than a fourth copy) for any future "skip straight to logging" shortcut.
- `lib/features/execution/execution_screen.dart`'s `_SessionReviewScreen` - shown between the unlogged-sets check and the note prompt in `_finishSession`, whenever at least one set was actually logged. Edits the same `_LoggedSetForm` controllers the exercise list itself owns (not copies), so any correction is picked up automatically once `_loggedEntriesFor` reads live text for the real DB write - no separate "apply review edits" step exists or is needed. Any future change to `_finishSession`'s flow needs to keep this in mind: tests that finish a session with a logged set must tap `'Confirm & finish'` here before whatever comes next.
- `SessionLogDao.updateLoggedSet()` - the one way to correct an already-saved set's reps/weight/RPE after a session is finished, reached by tapping a set on `CompletedWorkoutScreen`. Deliberately never touches `isPr` (see its own doc comment for why retroactive PR recalculation is out of scope).
- `lib/logic/one_rep_max.dart` — `estimateOneRepMax()` (Epley formula) and `bestEstimatedOneRepMax()`; `oneRepMaxScienceNote` is the honest citation shown via an info icon on the History screen and used by `estimatedOneRepMaxProvider` (`progress_providers.dart`).
- `lib/logic/percentage_prescription.dart` — lets a plan exercise's `weightIntensity` be a percentage (e.g. `"70%"`) instead of a flat weight, resolved against `estimatedOneRepMaxProvider` in `execution_screen.dart`.
- `lib/features/today/` — `TodayScreen` (the app's default landing tab, index 0), backed by `today_providers.dart`'s `nextScheduledSessionProvider` - derived from the Calendar tab's own already-invalidated `scheduledSessionsProvider`/`loggedPlanSessionIdsProvider`, so it needed no new invalidation call sites of its own.
- `lib/features/calendar/log_activity_flow.dart` — the ad-hoc "Log activity" dialog/flow, extracted out of `calendar_screen.dart` so both the Calendar tab and `TodayScreen`'s "Log activity" quick action can call the same `showLogActivityFlow()`.
- `lib/features/shared/info_dialog.dart` — `showInfoDialog(context, {title, content})`: the small "what does this mean?" dialog reused by every info icon added in the 2026-09-10 usability round (superset explanation, 1RM citation, partial-ROM citation) rather than each screen hand-rolling its own `AlertDialog`.
- `lib/logic/superset_info.dart` / `lib/logic/partial_rom_protocol.dart` — plain-language/citation content shown via the info icons above; kept as pure content files (no widget/DB dependency), matching `progression.dart`'s `progressionScienceNote` precedent.
- `lib/features/onboarding/whats_new_content.dart` / `whats_new_screen.dart` — the "What's new" feature for existing users, distinct from `onboarding_screen.dart`'s first-launch-only tour. `currentWhatsNewRevision` is a hand-maintained counter (bump it, and append to `whatsNewItems`, whenever something worth surfacing ships) compared against `AppPreferences.lastSeenWhatsNewRevision` - see that field's own doc comment for the gating logic between a brand-new install (its own onboarding stamps the revision immediately) and an existing device (starts at 0, so it's shown at least once).
- Supersets/circuits: `PlanExercises.supersetGroupId` (nullable `int`, scoped only to its own session - see its own doc comment), set/cleared via `PlanDao.setSupersetGroup()`/`clearSupersetGroup()`. `execution_screen.dart`'s `_groupedExercisesFor()` clusters plan exercises into `_SoloUnit`/`_SupersetUnit`s for rendering; `_SupersetCard` renders round-robin with per-round rest-timer triggering (see the Status entry above and the Conventions bullet below for the mechanics).
- `docs/linux-desktop-setup.md` / `docs/linux_setup.sh` — the one-time WSL2 install step (needs admin + a reboot, so it's a human step, documented not automated) plus an idempotent script that sets up a Flutter Linux build environment inside WSL2/Ubuntu and does a first `flutter build linux` of this project. Written 2026-09-14 ahead of having a Linux environment to test against (a plugin-by-plugin Linux-support read-through, and the pre-emptive `LinuxInitializationSettings` fix - see the Conventions bullet on `flutter_local_notifications`); the actual first build/bring-up happened 2026-09-15 (see that Status entry) and the doc's own "Update" section records what that found - Ubuntu's install needing to be re-run and its interactive first-launch worked around, the `[boot]\nsystemd=true` WSL requirement for a working D-Bus session, and two more `flutter_local_notifications_linux` methods needing the same platform-gap guard.
- `windows/build_msix.ps1` — builds/packs/signs the Windows MSIX package; run this instead of `dart run msix:create` (see its own header comment and the Conventions bullet below for why). `pubspec.yaml`'s `msix_config` (identity, `toast_activator.clsid` matching `WindowsInitializationSettings.guid`) and `windows/runner/utils.h`/`.cpp`'s `LoadSavedWindowBounds`/`SaveWindowBounds` (registry-backed window-size persistence) are the other Windows-packaging-adjacent pieces from the 2026-09-11 round.
- `lib/logic/period_comparison.dart` — `comparePeriods()` diffs two `PeriodSummary`s for the Progress tab's "vs previous period" delta cards; `lib/logic/summary_period.dart`'s `shiftedRange()` shifts an arbitrary `PeriodRange` by its own length, the one "previous/next" definition that works for a custom range (no calendar unit) as well as week/month.
- `WorkoutHistoryScreen` (`lib/features/history/workout_history_screen.dart`) takes optional `range`/`adHocOnly`/`title` params - null/false/null is the original all-time-history behaviour; a non-null `range` (with `workoutHistoryInRangeProvider`) is how the Progress tab's activity chips and custom-range picker both open a scoped, filtered view without a second screen.
- `buildProgressReportPdf()`'s optional `fullLog` param (`List<CompletedWorkout>`, from `SessionLogDao.getCompletedWorkoutsInRange()`) renders a full set-by-set/activity-by-activity "Full training log" section for the trainer-oriented "Share/Save full log (PDF)" export - separate from the existing aggregate-only summary report, not a mode of it.
- `lib/features/shared/photo_viewer_screen.dart` (`PhotoViewerScreen`) — the app's one full-screen, pinch-zoomable photo viewer; push it with a `fileNames`/`initialIndex`/`title` whenever a cropped `AttachmentImage` thumbnail needs a "see it full-size" tap target, rather than building another one-off viewer. Handles paging three ways (swipe, on-screen arrows, arrow keys) - see its own doc comment on why a plain `InteractiveViewer`-per-`PageView`-page needs `panEnabled` gated on zoom state, or swiping silently stops working.
- Exercise Library's "Select exercises to export" (its export menu → `_selectingForExport`/`_selectedExerciseIds` on `_ExerciseLibraryScreenState`) mirrors `edit_session_screen.dart`'s superset-grouping selection-mode pattern (checkbox-per-row, a count in the app bar, a close action) - copy this one for any future "pick a subset of a list" feature rather than inventing another shape. Feeds `buildLibraryJson`'s pre-existing `exercisesOverride` param at individual-exercise granularity.

## Conventions

- State management: **Riverpod** (`flutter_riverpod`). Providers live alongside the feature they back; the DB provider is in `lib/data/app_database_provider.dart`.
- Local DB: **Drift** (SQLite), via `drift` + `drift_flutter` (not `sqlite3_flutter_libs` directly — that package is end-of-life and `drift_flutter`'s `driftDatabase()` handles native setup). Run `dart run build_runner build --delete-conflicting-outputs` after changing any `@DriftDatabase`/table definitions to regenerate `*.g.dart`. Generated `**/*.g.dart` files are excluded from `flutter analyze` in `analysis_options.yaml`.
- Plan/backup file format: versioned JSON (`schema_version` field), defined in `schema/*.schema.json` — kept convertible with the spreadsheet template in `templates/`.
- Test commands: `flutter analyze`, `flutter test`. Full env needed for anything Android-related (see below) — `flutter analyze`/`flutter test` alone don't need it.
- DAO unit tests use `AppDatabase.forTesting(NativeDatabase.memory())` (see `test/data/*_dao_test.dart`) — fast, no platform channels needed.
- **Widget tests with a live Drift `AppDatabase`**: don't build the full app if you can avoid it. A `StreamProvider` watching a Drift `.watch()` query (e.g. `plansListProvider`) that's still mounted when the widget tree is torn down at test end schedules a stream-cleanup timer that fires *after* `flutter_test`'s "no pending timers" check already ran, failing the test with `A Timer is still pending`. `test/widget_test.dart` avoids this by pumping `ExerciseLibraryScreen` directly (a `FutureProvider`-only screen) instead of the full `HomeScreen`/`IndexedStack` (which keeps `PlanListScreen`'s `StreamProvider` alive on a hidden tab). If a future test genuinely needs the full app or a `StreamProvider`-backed screen, unmount it explicitly before the test ends: `await tester.pumpWidget(const SizedBox.shrink()); await tester.pump(); await db.close();` — in that order. **Update (2026-09-10): pumping `PlanListScreen` directly hangs outright, not just "Timer still pending" at teardown.** Tried while adding Plans-list search - even the most minimal possible test (bare `pumpWidget(PlanListScreen())`, two `pump()` calls, one text assertion, zero interaction) hit the full test timeout with proper `SizedBox.shrink()`/`db.close()` teardown already in place, confirmed via a 30-second `Timeout` override to fail fast rather than waiting the default 10 minutes. This is the same unexplained-hang category already documented below for `add_exercise_to_plan_screen.dart` - not isolated to a specific interaction, not fixed by replacing `pumpAndSettle()` with bounded `pump()` calls (tried both). **Don't attempt a `PlanListScreen` widget test at all on this machine** - ship the feature with manual/live emulator verification instead, same as that other screen.
- **Windows-only flakiness**: if `flutter build`/`flutter test` fails with "Flutter failed to delete file at ...\build\native_assets\windows\sqlite3.dll" (a file-lock, likely Windows Defender scanning it right after a process exits), `rm -rf build .dart_tool` and retry — don't chase it as a code bug.
- **On this machine, neither PowerShell's `Compress-Archive` nor .NET Framework's `System.IO.Compression.ZipFile.CreateFromDirectory` (as exposed to Windows PowerShell 5.1) can be trusted to produce a zip with forward-slash entry names when the source has subfolders** - both write backslash-separated names (`xl\workbook.xml`) instead, which the zip spec requires as `/` and which this app's own `xlsx_reader.dart` (or any standards-conforming zip reader, including real Excel) won't match. Found hand-patching the `.xlsx` templates for the video-embedding feature (2026-09-22) - confirmed via `[System.IO.Compression.ZipFile]::OpenRead(...).Entries.FullName` showing backslashes, and via the app's own parser failing with "missing workbook.xml" against the first patched file. Fix: build the archive entry-by-entry with `ZipArchive`/`ZipFileExtensions.CreateEntryFromFile(archive, sourcePath, explicitForwardSlashName, ...)`, passing the entry name explicitly rather than letting either higher-level API derive it from the filesystem path.
- Package API notes for versions pinned as of Phase 1 (check before assuming an older API from memory/docs): `csv: ^8.0.0` uses `Csv(lineDelimiter: ...).decode(text)`, not the old `CsvToListConverter`. `file_picker: ^12.1.1` uses static `FilePicker.pickFile(...)`/`pickFiles(...)` (no `.platform` getter) and `PlatformFile.readAsBytes()` (the `withData`/`.bytes` pattern from older versions is deprecated).
- **Timers that must survive backgrounding** (Phase 2's rest timer, and anything similar later): never count down tick-by-tick. Store a fixed `DateTime` end point and always recompute `remaining = endTime.difference(now)` from the current wall-clock time - see `lib/logic/rest_timer.dart`. A periodic `Timer` (in `lib/features/execution/rest_timer_controller.dart`) only exists to trigger UI repaints; it isn't the source of truth, so it doesn't matter if ticks are missed/delayed while the app is backgrounded.
- `fl_chart`'s default Y-axis label interval can pick ugly values that overlap (e.g. showing both 70 and 72 when `maxY` is 72) - round `maxY` to a clean multiple of a chosen interval yourself rather than trusting the default (see `history_screen.dart`).
- A `ListTile` with a multi-widget `trailing` (e.g. two buttons in a `Wrap`) can squeeze `title` into a too-narrow column, causing severe character-by-character text wrapping - this actually happened in `plan_import_screen.dart`'s unmatched-exercise card. Prefer a `Column` (title/subtitle on top, an `OverflowBar` of actions below) over `ListTile.trailing` whenever trailing content is more than a single small icon/button.
- **One-shot `FutureProvider`s don't notice direct DB writes from another screen.** `filteredExercisesProvider`/`exerciseCategoriesProvider` (`exercise_library_providers.dart`) are computed once and cached; since `HomeScreen`'s `IndexedStack` keeps every tab mounted from app start, a write that happens on a *different* tab (Settings, Plans import) never triggers a rebuild on the Exercises tab unless something explicitly calls `ref.invalidate(...)` on both providers. This bit three separate call sites before they were all found and fixed by manual testing: `settings_screen.dart`'s delete-all and restore-backup, `plan_import_screen.dart`'s `_createCustom` (spreadsheet import), and `plan_list_screen.dart`'s `_importFromJson`. Any code path that creates, edits or deletes exercises must call `invalidateExerciseListProviders(ref)` (`lib/features/shared/exercise_list_invalidation.dart`), which refreshes every cached copy of the library: the library list, categories, creator and equipment filters, the import matcher (`allExercisesForMatchingProvider`) and execution mode's `exerciseLookupProvider`. Before 2026-10-07 each call site kept its own partial list, and several missed the matcher and the lookup - a plan-file import followed by a spreadsheet import showed every new exercise as unmatched until a restart. Add any new exercise-list `FutureProvider` to that helper, not to individual call sites. Reactive `.watch()`-backed providers (like `plansListProvider`) don't have this problem, only one-shot `FutureProvider`s do.
- **Every whole-file import is all-or-nothing.** `importPlanJson`, `importLibraryJson`, `importBackupJson` and `applyIncomingPlan` each run in one `db.transaction`, and turn any failure into their own format exception (`PlanJsonFormatException` etc.), which the screens show as a message. A new importer must do the same: before 2026-10-14 a damaged file left half its data written, a damaged sync version deleted the local plan and its logged workouts, and the error went uncaught so nothing appeared on screen. Read a picked file's text with `decodeJsonObject()` (`lib/import/json_object.dart`), not `jsonDecode(...) as Map`, and catch its `FormatException` - that covers non-JSON text and JSON that isn't an object. Pinned by `test/import/damaged_import_files_test.dart` and `backup_restore_rollback_test.dart`.
- **Backup schema note:** `schema/backup.schema.json`'s `sessionLog` requires both `week_number` and `day` alongside `plan_id`/`session_name` - a session name (e.g. "Push Day") can legitimately repeat across weeks in the same plan, so name+plan alone is ambiguous for re-linking a restored log to the correct `PlanSessions` row. See `test/export/backup_roundtrip_test.dart`'s week-disambiguation test.
- Package API note (Phase 3, in addition to Phase 1's csv/file_picker notes): `cryptography: ^2.9.0`'s `Argon2id`/`AesGcm.with256bits()` APIs are used as-is for `lib/security/backup_encryption.dart` - no wrapper needed beyond the envelope format.
- **Real `dart:io` file reads/writes can hang inside a `testWidgets` test on this machine, specifically when the I/O happens *after* `pumpWidget` has run.** Reproduced and isolated during Phase 4 (see `test/features/incoming_share_handler_test.dart`'s file header comment): a plain `File.writeAsString`/`readAsString` call after any `pumpWidget()` in the same test blocked for the full 10-minute test timeout on this Windows setup, every time, regardless of `tearDown` handling - a `testWidgets`/Windows event-loop interaction, not a product bug (a plain `test()` doing the same I/O, e.g. `test/data/local_storage_test.dart`, is unaffected). If a widget-tested code path needs to read/write real files, structure it like `lib/features/sharing/incoming_share_handler.dart`: split a thin `dart:io` wrapper (untested, or tested outside `testWidgets`) from the actual logic, which takes content as a `String`/`bytes` parameter so tests can supply it directly without touching the filesystem. **Update (2026-09-22): this extends to `rootBundle.loadString`/`rootBundle.load` too, not just `dart:io`, and not only *after* `pumpWidget`.** Found adding `templates_screen.dart`'s direct-import button (`_importWgerLibrary`, reads the bundled `templates/wger_starter_library.csv` asset): `await rootBundle.loadString(...)` as the very first line of a `testWidgets` callback - before any `pumpWidget` call at all - still hung for the full test timeout (confirmed via a backgrounded run left to sit rather than assumed; killed manually after several minutes with no output past the line before the await). Same fix shape applies: don't drive a real asset load through a widget test's tap; verify that thin glue live instead, and keep the widget test scoped to a screen that's handed content directly (`ExerciseLibraryImportScreen(csvContent: ...)`, already covered by `exercise_library_import_screen_test.dart`).
- Package API note (Phase 4): `receive_sharing_intent` is pinned to `1.8.1`, not `^1.9.0` - 1.9.0 bumped its Android `compileSdk` to 37, which errored on this machine (the auto-installed SDK Platform 37 registered under a non-standard `android-37.0` folder name that Gradle's target resolution couldn't match against the plugin's hardcoded `android-37` requirement - the same class of Android-SDK-tooling unreliability noted below, just triggered via Gradle's own auto-installer this time rather than `sdkmanager` directly). 1.8.1's Dart API (`ReceiveSharingIntent.instance.getInitialMedia()`/`getMediaStream()`/`reset()`, `SharedMediaFile`) is identical to 1.9.0's for what this project uses.
- **Gradle note** (`android/build.gradle.kts`): a `subprojects` block forces every included Gradle module (our own app *and* any plugin) to Java/Kotlin JVM target 17 consistently. Added in Phase 4 because `receive_sharing_intent` 1.8.1's own `build.gradle` sets Kotlin's `jvmTarget` to 17 without updating its Java `compileOptions` to match, which Gradle rejects as "Inconsistent JVM Target Compatibility" - a bug in that plugin's build config, not something fixable from our app's own `build.gradle.kts` alone.
- **This project's SQLite connections don't enforce foreign keys - don't rely on `ON DELETE CASCADE` ever actually firing.** `MaintenanceDao.wipeAllData()` already documented this (deletes children before parents "regardless of whether SQLite's foreign_keys pragma happens to be on"), but `PlanDao.deletePlan()` didn't follow its own doc/test's claim ("cascades to sessions and exercises") until Phase 5 - it only ever deleted the `Plans` row, silently leaving orphaned `PlanSessions`/`PlanExercises` rows behind. On a machine that's never installed this test cert: run the script once, then trust `build\windows\x64\runner\Release\test_cert.cer` machine-wide from an **elevated** PowerShell (`certutil -addstore Root <path>`) - per-user trust stores are not sufficient for `Add-AppxPackage`'s signature validation, confirmed live (HRESULT 0x800B0109 until the cert was in `LocalMachine\Root` specifically).
- **`Get-WinEvent -FilterHashtable @{LogName='Application'; ProviderName='SideBySide'}` reads a Windows SxS activation failure's actual underlying cause without needing admin rights** - unlike `sxstrace.exe`'s own trace-collection mode (`sxstrace Trace -logfile:...`), which does require elevation to start a new ETW session. Worth remembering for any future "Side-by-Side-Konfiguration ist ungueltig"/"side-by-side configuration is invalid" error on this machine: the generic error message never names the actual missing/mismatched dependency, but the event log entry it silently writes does.
- **A Flutter Windows app's accessibility/semantics tree does not populate for a plain `System.Windows.Automation` query from an external script** (tried live, 2026-09-11, driving the packaged app to test the MSIX notification fix) - `AutomationElement.FindAll` against the app's window only ever returned one opaque `FLUTTERVIEW` pane node, even after a delay. Automating this app's UI from outside (PowerShell, a test harness) needs raw coordinate-based mouse clicks against a screenshot of the actual window (`GetWindowRect` + `CopyFromScreen` + `SetCursorPos`/`mouse_event`) - the same technique already used for the Android emulator - not semantic element lookup.
- **Driving/screenshotting a Flutter Linux app inside WSL when WSLg's own window relay doesn't work (2026-09-15).** WSLg is supposed to show each Linux GUI app as a native Windows window via a `vail.exe` relay process, but that process never appeared in this environment, and even a trivial `xclock` produced a genuinely blank captured screenshot on WSLg's own display regardless of GDK backend or software/hardware GL - a real, environment-level limitation, not an app bug. Worked around with a self-contained `Xvfb` virtual framebuffer (`Xvfb :98 -screen 0 1280x800x24`, a fresh unused display number) driven by `xdotool` (input) and ImageMagick's `import -window root` (screenshots) - entirely independent of WSLg's own relay. **No window manager is needed for this** - one was tried (`fluxbox`) to fix an apparent click-to-focus problem, but it broke `xdotool mousemove`'s XTEST pointer warping outright (motion silently no-op'd once fluxbox took over the display); the real fix was combining `mousemove` and `click` into one `xdotool` invocation (`xdotool mousemove X Y click 1`) instead of separate calls, which was the actual reliability issue, not focus. A hung `xdotool ... --sync` call (from a stopped background task) also permanently stuck one display's pointer position - don't debug a stuck display, just move to a fresh display number. Keep a launched GUI process alive across `wsl.exe` invocations by using a tool invocation that itself stays alive for as long as the process needs to run (this project's agent tooling: a backgrounded call whose own process is the app's parent) - a plain `cmd &` backgrounded inside a short-lived `wsl -d <distro> bash -c "..."` call does not reliably survive once that outer command returns, even with `nohup`/`disown`/`setsid`.
- **Testing this app in a real VirtualBox Ubuntu VM (as opposed to WSL2), found 2026-09-15.** Set up for exactly the case WSL2/WSLg can't cover well - a genuine desktop compositor with no forced rendering-backend workarounds. Setup gotchas, in the order they'll actually bite: (1) VirtualBox's `VMSVGA` graphics controller emulation causes a real Linux guest kernel to spam `vmwgfx *ERROR* seems to be running on an unsupported hypervisor` and effectively never finish booting - switch **Settings > Display > Graphics Controller to `VBoxSVGA`** before ever booting the installer. (2) A `watchdog: BUG: soft lockup - CPU#0 stuck for Ns!` very early in boot, on a Windows host that also has Hyper-V enabled (e.g. for WSL2, as this project's own Linux build setup does) - VirtualBox gets forced onto the Windows Hypervisor Platform (WHP) backend instead of raw VT-x, which has known CPU/APIC timer emulation instability that gets worse with higher vCPU counts. Fixed here by simply lowering the VM's assigned CPU count (16 → a much smaller number) rather than the more disruptive option of disabling Hyper-V entirely (`bcdedit /set hypervisorlaunchtype off` + reboot, which also breaks WSL2 until reverted) - try the cheap fix first. (3) **Host-side synthetic mouse input (Win32 `SendInput`/`mouse_event` from PowerShell) does not reliably reach a VirtualBox guest, even with correct coordinates, confirmed elevation parity, and verified OS-level foreground focus** - confirmed by watching the guest's own raw input device with `evtest /dev/input/eventN` (the actual VirtualBox USB Tablet device) while sending host-side clicks: zero events arrive at the driver level, no matter the method. A real physical click from an actual human, on the exact same window, registers instantly and correctly. No root cause found (tried: elevation mismatch - fixed, ruled out; DPI virtualization - ruled out, host is 100% scale; multi-monitor normalization via `MOUSEEVENTF_VIRTUALDESK` vs. primary-monitor-only normalization - both ruled out; GNOME hot-corner interference - real, fixable via `gsettings set org.gnome.desktop.interface enable-hot-corners false`, but not the core issue). **Practical conclusion: don't invest further in host-to-VirtualBox-guest synthetic input automation - drive the VM interactively with the user's own clicks instead, verifying state via `VBoxManage controlvm <name> screenshotpng <path>`** (which works perfectly and needs no guest-side cooperation at all, unlike WSLg's own screenshot story). (4) SSH access is the reliable way to run commands/install packages/transfer files: enable `openssh-server` in the guest, add a NAT port-forward (guest 22 → some host port), and set up key-based auth (`ssh-keygen`, then manually append the `.pub` to the guest's `~/.ssh/authorized_keys` once, since there's no non-interactive way to seed it otherwise) - passwordless sudo on this throwaway test VM avoids the exact "sudo hangs forever with no TTY to prompt" problem already documented for WSL. (5) The already-built Linux app bundle from a WSL checkout can be copied straight into a VirtualBox VM via `scp` from the `\\wsl.localhost\<distro>\...` UNC path (Windows can read WSL's filesystem directly) - no need to rebuild Flutter from scratch on the VM. (6) To actually launch a GUI app on the guest's real (already-logged-in) desktop session over SSH - which is a *separate* login session from the graphical one - export `XDG_RUNTIME_DIR=/run/user/<uid>` and `WAYLAND_DISPLAY=wayland-0` (find the exact socket name via `ls /run/user/<uid>/`) before running the binary; a bare SSH shell has neither set.
- **WSL2/Ubuntu gotchas, found bringing up the Linux desktop build (2026-09-15) - relevant any time WSL is used, not just for a Flutter build.** (1) `wsl --install -d Ubuntu`'s post-reboot flow can leave zero distros actually installed (`wsl --list --verbose` showing none) even though the WSL2 engine/kernel itself is up - re-running the same install command then works, but its interactive first-launch username/password prompt hangs forever if driven non-interactively; create the Linux user directly as root instead (`useradd -m -s /bin/bash -G sudo <user>`, `chpasswd`, `/etc/wsl.conf`'s `[user]` `default=<user>`) rather than fighting the wizard. (2) WSL auto-imports the Windows `PATH` (interop) into the Linux shell, and that Windows `PATH` contains space-laden entries (`C:\Program Files\...`) - an unquoted `export PATH=$SOMETHING:$PATH` word-splits on those spaces with a confusing `export: 'Files/...': not a valid identifier` error; always quote the whole assignment. (3) A stock WSL2 Ubuntu instance has **no D-Bus session bus** (`/run/user/1000/bus` doesn't exist) unless systemd is enabled - fix with `[boot]\nsystemd=true` in `/etc/wsl.conf` plus `wsl --shutdown` + relaunch (no admin/reboot needed on Ubuntu 24.04+, which ships real systemd-in-WSL2 support) - anything that touches D-Bus (notifications, some GTK/desktop-integration APIs) will fail without this. (4) **Never grant a WSL dev user passwordless sudo (`NOPASSWD:ALL`) just to make a script's `sudo` calls work non-interactively** - that's a real security weakening, not a convenience shortcut, and shouldn't happen without being asked for explicitly (this was attempted once and correctly blocked). Instead, run root-requiring steps directly as root (`wsl -d <distro> -u root bash -c "..."`) - no password needed since there's nothing to authenticate when already root.
- **A DAO method built on `into(table).insertOnConflictUpdate(companion)` (i.e. `upsertExercise`) is a real INSERT under the hood, and Drift validates the companion as if it might have to perform one - every non-nullable, no-default column must be present, even when the row is known to already exist and only a conflict-triggered UPDATE will actually run.** Found live (2026-09-11) breaking the plan-photo-zip import: `_attachPictureIfAny` (`plan_import_screen.dart`) called `upsertExercise` with a companion carrying only `id`/`imagePath`/`imagePaths`, which threw `InvalidDataException` every time (missing `name`/`category`/etc.) - silently aborting the caller mid-function, after the exercise row itself had already been created but before the screen's own `setState`/`invalidate` calls ever ran, which read as "the button does nothing" with no visible error anywhere. **Any partial, single-or-few-column write to an existing row must use a dedicated `update(table)..where(...)`-based DAO method** (see `setFavorite`, and the new `ExerciseDao.attachImages`) - never route it through an upsert helper meant for full-row writes.

- **A correctly-implemented, already-tested function with an optional param for something real (attachments, a directory, an override) is not proof the param is actually passed at every call site - check the call site, not just the function.** `buildBackupJson()`/`importBackupJson()`'s `attachmentsDirectory` param had exhaustive round-trip test coverage (`backup_roundtrip_test.dart`) proving the *function* correctly embeds/restores photo bytes when given a directory - but `settings_screen.dart`'s real "Export full backup"/"Restore from backup" buttons called both functions without ever passing it, silently dropping every exercise photo from a real backup with no error (found 2026-09-14, tracing a live "how much backup already works" question rather than a bug report). Both the DAO/pure-logic layer *and* its actual UI call sites need checking before trusting a feature is wired up end-to-end - a green test suite for the former says nothing about the latter.
- **`flutter_test`'s default `find.text()`/`find.textContaining()` (`skipOffstage: true`) can report zero matches for a widget that is genuinely built and present, just scrolled below the fold of a plain `ListView` on the default test viewport (800×600-ish)** - confirmed live (2026-09-14) writing `progress_screen_no_weight_test.dart`: content well down `progress_screen.dart`'s `ListView` (past the streak card, summary cards, chart) matched with `skipOffstage: false` (and via `tester.allWidgets`) but not with the default finder settings, despite no `Offstage` widget anywhere in the ancestor chain - flutter_test's offstage check evidently also treats content outside a `Scrollable`'s current viewport this way, not only literal `Offstage` widgets. **Don't conclude a feature is missing/broken from a bare `findsNothing` on a long scrolling screen** - retry with `skipOffstage: false` (safe for a presence-only assertion; use `tester.ensureVisible()`/`dragUntilVisible()` instead if the test needs to actually interact with the widget) before assuming the code is wrong.
- **A skipped exercise's set rows still exist and still hold their prefilled reps/weight hints** (`_formsFor` creates them whenever the card builds). Anything that scans `formsByExerciseRowId` for "typed but not logged" must exclude `skippedExerciseRowIds`, or skipping an exercise raises an "Unlogged sets" prompt whose "Log & finish" logs the skipped exercise - see `_unloggedFilledForms`.
- **i18n is deliberately partial.** Only `settings_screen.dart`'s "Units & display" section uses `AppLocalizations`; keep plain English literals everywhere else until a dedicated full-migration pass, rather than adding one-off ARB keys.
- **The first logged weight for an exercise is always a PR**, so `_SetRow` shows `Icons.emoji_events`, not `Icons.check_circle`. In tests, assert on the shared `'Undo - edit this set again'` tooltip instead of a specific icon.
- **The debug-mode banner hit-test-intercepts the AppBar's top-right icon** (the Settings gear, and the Plan/Library export menus) on Windows debug builds. Use a release build to test those taps.
- **Android emulator compositor stalls:** if the screen stops updating and `uiautomator dump` keeps returning a near-empty tree for 30s+ while the process is alive, `am force-stop` + relaunch the app (not the AVD) and check whether the data from just before the freeze landed.
- **A Windows toast that won't update or cancel: check Focus Assist first.** With it on, `updateProgressBar`/`cancel` report success while the Action Center entry stays frozen.
- **`whatsNewItems` icons:** pick an icon already used as a literal `Icon(Icons.x)` elsewhere in `lib/` (`grep -rohE "Icon\(\s*Icons\.[a-zA-Z_0-9]+" lib/`), and check it in the built app. Some `IconData` constants render blank in this SDK's tree-shaken font.
- **Dropbox build folders:** remove directories with PowerShell `Remove-Item -Recurse -Force` (git-bash `rm` fails on Dropbox's reparse points; retry on a transient "used by another process"), and copy into a fully removed destination, never `cp -r` over a partial one.

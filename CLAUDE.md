# Training App

A local-first, privacy-focused training/workout organization app. Cross-platform (Android → iOS → Windows) via Flutter, built and validated on Android first per the phased plan below.

**Status:** Phase 5 (multi-device sync) complete, plus five follow-up rounds of user-requested additions layered on top (not a numbered phase - see `docs/TODO.md` for the backlog these came from). **Four more real reports, a later session (2026-09-04)**: (1) numeric-only fields across the app (`execution_screen.dart`'s Reps/Weight/RPE, `body_measurements_screen.dart`, `add_exercise_to_plan_screen.dart`, `edit_session_screen.dart`, `calendar_screen.dart`) only set `keyboardType`, which merely picks which on-screen keyboard shows - a physical/emulator keyboard could type arbitrary text (letters, multiple decimal points) straight into a field that later gets blindly `int.tryParse`/`double.tryParse`d, and a bad value would silently vanish rather than error. **Progression suggestions rebuilt on cited research, not "gym bro science" (2026-09-05)**: the user directly challenged the auto-progression feature's assumptions - what was it actually based on, and could it be rebuilt on real evidence with that evidence stated in the app? The prior version (`lib/logic/progression.dart`) added a fixed kg amount (5 / 2.5 / 1.25 by experience level) the instant a single session hit a rep target, treated any 10+ day gap as "missed," and told a plateaued lifter to just repeat the weight and "focus on form" - all plausible-sounding but not tied to any specific source. Researched via WebSearch/WebFetch (the full ACSM 2009 position stand PDF, a double-progression review, RPE/RIR autoregulation literature, deload-practice surveys, and detraining meta-analyses) and rebuilt around three cited changes: (1) the "2-for-2 rule" - weight now only increases after *exceeding* the rep target (by at least 1) on two consecutive sessions at the same weight, not the instant it's hit once; a single good day no longer permanently changes the suggestion. This is the literal wording of Ratamess et al. (2009), "Progression Models in Resistance Training for Healthy Adults" (ACSM position stand, Medicine & Science in Sports & Exercise 41(3)): "a 2-10% ... increase in load be applied when the individual can perform the current workload for one to two repetitions over the desired number on two consecutive training sessions." The load increase itself changed from a fixed kg amount to a percentage of current weight (7.5% / 5% / 2.5% by experience level, all inside that cited 2-10% range - ACSM ties the exact percentage to exercise/muscle-mass size, which this app doesn't categorize exercises by, so experience level is used as a documented practical proxy instead), rounded to the nearest half-kilogram with a 0.5kg practical floor (`_roundToPracticalIncrement`). (2) A genuine plateau (3+ sessions stalled at the same weight, missing the target every time) now suggests a 10% deload rather than "repeat and focus on form" - citing deload-practice literature (Bell et al., 2023, on coaches' deloading practices) while being honest in the in-app text that evidence on how much a deload itself helps is mixed, not a guaranteed fix. (3) `missedSessionThresholdDays` moved from an arbitrary 10 to 21, and a new `longLayoffThresholdDays` (42) suggests an actual weight *reduction* rather than just a repeat - grounded in a training-cessation meta-analysis (Bosquet et al.) showing force decline is unremarkable under two weeks but becomes significant around the three-week mark. Also added light RPE-awareness: `SessionLogDao.getProgressionHistory()` now reduces a session to the *fewest* reps and *highest* RPE among sets tied for the session's top weight (previously an arbitrary tied set won, which could let one easy set on an otherwise-failed day look like a clean success) - `ProgressionHistoryEntry` gained a nullable `rpe` field, and a 2-for-2 qualifying session with a near-failure RPE (9.5+, per the Zourdos et al. RIR-based RPE scale) caps the increase at the smallest tier regardless of stated experience level. Per the user's explicit request, the app now says what this is based on: an info icon next to History screen's "Suggested next session" card opens a dialog with `progressionScienceNote` (single source of truth for the in-app explanation, kept next to the logic itself so they can't drift apart), and the Settings toggle's description points to it. This is a genuine behavior change, not just wording - `test/logic/progression_test.dart` was rewritten end-to-end (two-consecutive-session gating, percentage rounding, RPE capping, deload, the two layoff tiers) rather than patched, and `test/features/history_screen_experience_level_test.dart`'s seed data changed from one qualifying session to two (the old single-session setup no longer exercises the level-dependent branch at all under the new rule).

**A real-device report closed the loop on the Phase 4 share-intent design (2026-09-05)**: reported live after installing a release build on a physical phone - Android started offering Training App as a candidate handler for opening PDFs and even for installing other APKs, from the system-wide "Open with"/share sheets, completely unrelated to training data. ## Where things are

- `docs/development-plan.md` — the authoritative phased plan (Phase 0 through Phase 8). Read this in full before starting work; each phase lists what to build, what to test, and its exit criteria. Do not skip ahead to a later phase's features before the current phase's exit criteria are met.
- `templates/` — the user-facing spreadsheet template (`.xlsx` and `.csv`) for authoring a training plan outside the app, per the Phase 1 "spreadsheet import" feature. Both files define the plan schema: one row per exercise-in-a-session, columns `Week, Day, Session Name, Order, Exercise Name, Sets, Reps, Weight/Intensity, Rest (sec), Notes, Video URL`. The `.xlsx` also has an "Instructions" tab explaining each column and a "Plan" tab with example rows plus dropdown/number validation — use it as the spec for the import parser's expected shape.
- `seed-data/` — 38 sample strongman exercises (`.xlsx` and `.csv`) for seeding and testing the exercise library in Phase 1. Columns: `Exercise ID, Exercise Name, Category, Movement Pattern, Muscle Group(s), Equipment, Difficulty, Measurement Type, Description / Cues, Safety Notes, Video Reference`. The `.xlsx` has a "Legend" tab explaining each column — note its column set is the exercise-library schema, distinct from (but related to) the plan-template schema in `templates/`. `Measurement Type` matters: several exercises are scored by distance/time rather than weight×reps, which should drive which input fields the session-logging screen shows for a given exercise.
- `schema/` — versioned JSON Schema definitions (`exercise.schema.json`, `plan.schema.json`, `backup.schema.json`) for the plan/backup file format described in Phase 0/3, kept convertible with the `templates/` spreadsheet.
- `lib/data/app_database.dart` — the Drift `AppDatabase` (`exercises`, `plans`, `plan_sessions`, `plan_session_dates`, `plan_exercises` tables, defined in `lib/data/tables/`). Opened via `package:drift_flutter`'s `driftDatabase()` helper, exposed to the widget tree via `appDatabaseProvider` (Riverpod) in `lib/data/app_database_provider.dart`. DAOs live in `lib/data/daos/` (`ExerciseDao`, `PlanDao` — the latter also defines plain-Dart input/result types like `PlanSessionInput`, `PlanDetails`, `ScheduledSession` since Drift only generates row classes for `@DriftDatabase` tables, not hand-written accessor types — import `lib/data/daos/plan_dao.dart` directly to use them, `app_database.dart` doesn't re-export them).

Called once at app startup (see `main.dart`'s `_startupProvider`) — safe to call repeatedly since it upserts by id.
- `lib/import/plan_spreadsheet_parser.dart` — the plan-template CSV parser (`parsePlanCsv`), exercise-name matcher (`matchExercisesAgainstLibrary`), and week/session grouper (`groupIntoSessions`). Columns are matched by header name, not position, so a reordered template still parses. Per-row problems (missing required value, unparseable number) are collected as `PlanImportRowError`s rather than thrown, so one bad row doesn't block importing the rest of the file; only structural problems (a required column missing entirely, an empty file, or a file over `maxImportRows`) throw `PlanImportFormatException`. Exercise-name matching is exact-after-normalization only (lowercase, apostrophes stripped, punctuation/whitespace collapsed) — deliberately not fuzzy/edit-distance, so it never silently matches the wrong exercise; unmatched rows surface in `PlanImportScreen` for the user to resolve (pick an existing exercise or add a custom one).

## Conventions

- State management: **Riverpod** (`flutter_riverpod`). Providers live alongside the feature they back; the DB provider is in `lib/data/app_database_provider.dart`.
- Local DB: **Drift** (SQLite), via `drift` + `drift_flutter` (not `sqlite3_flutter_libs` directly — that package is end-of-life and `drift_flutter`'s `driftDatabase()` handles native setup). Run `dart run build_runner build --delete-conflicting-outputs` after changing any `@DriftDatabase`/table definitions to regenerate `*.g.dart`. Generated `**/*.g.dart` files are excluded from `flutter analyze` in `analysis_options.yaml`.
- Plan/backup file format: versioned JSON (`schema_version` field), defined in `schema/*.schema.json` — kept convertible with the spreadsheet template in `templates/`.
- Test commands: `flutter analyze`, `flutter test`. Full env needed for anything Android-related (see below) — `flutter analyze`/`flutter test` alone don't need it.
- DAO unit tests use `AppDatabase.forTesting(NativeDatabase.memory())` (see `test/data/*_dao_test.dart`) — fast, no platform channels needed.
- **Widget tests with a live Drift `AppDatabase`**: don't build the full app if you can avoid it. A `StreamProvider` watching a Drift `.watch()` query (e.g. `plansListProvider`) that's still mounted when the widget tree is torn down at test end schedules a stream-cleanup timer that fires *after* `flutter_test`'s "no pending timers" check already ran, failing the test with `A Timer is still pending`. `test/widget_test.dart` avoids this by pumping `ExerciseLibraryScreen` directly (a `FutureProvider`-only screen) instead of the full `HomeScreen`/`IndexedStack` (which keeps `PlanListScreen`'s `StreamProvider` alive on a hidden tab). If a future test genuinely needs the full app or a `StreamProvider`-backed screen, unmount it explicitly before the test ends: `await tester.pumpWidget(const SizedBox.shrink()); await tester.pump(); await db.close();` — in that order. **Update (2026-09-10): pumping `PlanListScreen` directly hangs outright, not just "Timer still pending" at teardown.** Tried while adding Plans-list search - even the most minimal possible test (bare `pumpWidget(PlanListScreen())`, two `pump()` calls, one text assertion, zero interaction) hit the full test timeout with proper `SizedBox.shrink()`/`db.close()` teardown already in place, confirmed via a 30-second `Timeout` override to fail fast rather than waiting the default 10 minutes. This is the same unexplained-hang category already documented below for `add_exercise_to_plan_screen.dart` - not isolated to a specific interaction, not fixed by replacing `pumpAndSettle()` with bounded `pump()` calls (tried both). **Don't attempt a `PlanListScreen` widget test at all on this machine** - ship the feature with manual/live emulator verification instead, same as that other screen.
- **Windows-only flakiness**: if `flutter build`/`flutter test` fails with "Flutter failed to delete file at ...\build\native_assets\windows\sqlite3.dll" (a file-lock, likely Windows Defender scanning it right after a process exits), `rm -rf build .dart_tool` and retry — don't chase it as a code bug.
- **On this machine, neither PowerShell's `Compress-Archive` nor .NET Framework's `System.IO.Compression.ZipFile.CreateFromDirectory` (as exposed to Windows PowerShell 5.1) can be trusted to produce a zip with forward-slash entry names when the source has subfolders** - both write backslash-separated names (`xl\workbook.xml`) instead, which the zip spec requires as `/` and which this app's own `xlsx_reader.dart` (or any standards-conforming zip reader, including real Excel) won't match. Found hand-patching the `.xlsx` templates for the video-embedding feature (2026-09-22) - confirmed via `[System.IO.Compression.ZipFile]::OpenRead(...).Entries.FullName` showing backslashes, and via the app's own parser failing with "missing workbook.xml" against the first patched file. Fix: build the archive entry-by-entry with `ZipArchive`/`ZipFileExtensions.CreateEntryFromFile(archive, sourcePath, explicitForwardSlashName, ...)`, passing the entry name explicitly rather than letting either higher-level API derive it from the filesystem path.
- Package API notes for versions pinned as of Phase 1 (check before assuming an older API from memory/docs): `csv: ^8.0.0` uses `Csv(lineDelimiter: ...).decode(text)`, not the old `CsvToListConverter`. `file_picker: ^12.1.1` uses static `FilePicker.pickFile(...)`/`pickFiles(...)` (no `.platform` getter) and `PlatformFile.readAsBytes()` (the `withData`/`.bytes` pattern from older versions is deprecated).
- **Timers that must survive backgrounding** (Phase 2's rest timer, and anything similar later): never count down tick-by-tick. Store a fixed `DateTime` end point and always recompute `remaining = endTime.difference(now)` from the current wall-clock time - see `lib/logic/rest_timer.dart`. A periodic `Timer` (in `lib/features/execution/rest_timer_controller.dart`) only exists to trigger UI repaints; it isn't the source of truth, so it doesn't matter if ticks are missed/delayed while the app is backgrounded.
- `fl_chart`'s default Y-axis label interval can pick ugly values that overlap (e.g. showing both 70 and 72 when `maxY` is 72) - round `maxY` to a clean multiple of a chosen interval yourself rather than trusting the default (see `history_screen.dart`).
- A `ListTile` with a multi-widget `trailing` (e.g. two buttons in a `Wrap`) can squeeze `title` into a too-narrow column, causing severe character-by-character text wrapping - this actually happened in `plan_import_screen.dart`'s unmatched-exercise card. Prefer a `Column` (title/subtitle on top, an `OverflowBar` of actions below) over `ListTile.trailing` whenever trailing content is more than a single small icon/button.
- **One-shot `FutureProvider`s don't notice direct DB writes from another screen.** `filteredExercisesProvider`/`exerciseCategoriesProvider` (`exercise_library_providers.dart`) are computed once and cached; since `HomeScreen`'s `IndexedStack` keeps every tab mounted from app start, a write that happens on a *different* tab (Settings, Plans import) never triggers a rebuild on the Exercises tab unless something explicitly calls `ref.invalidate(...)` on both providers. This bit three separate call sites before they were all found and fixed by manual testing: `settings_screen.dart`'s delete-all and restore-backup, `plan_import_screen.dart`'s `_createCustom` (spreadsheet import), and `plan_list_screen.dart`'s `_importFromJson`. Any *new* code path that creates/deletes exercises outside the Exercise Library screen itself needs the same two `ref.invalidate` calls - reactive `.watch()`-backed providers (like `plansListProvider`) don't have this problem, only one-shot `FutureProvider`s do.
- **Backup schema note:** `schema/backup.schema.json`'s `sessionLog` requires both `week_number` and `day` alongside `plan_id`/`session_name` - a session name (e.g. "Push Day") can legitimately repeat across weeks in the same plan, so name+plan alone is ambiguous for re-linking a restored log to the correct `PlanSessions` row. See `test/export/backup_roundtrip_test.dart`'s week-disambiguation test.
- Package API note (Phase 3, in addition to Phase 1's csv/file_picker notes): `cryptography: ^2.9.0`'s `Argon2id`/`AesGcm.with256bits()` APIs are used as-is for `lib/security/backup_encryption.dart` - no wrapper needed beyond the envelope format.
- **Real `dart:io` file reads/writes can hang inside a `testWidgets` test on this machine, specifically when the I/O happens *after* `pumpWidget` has run.** Reproduced and isolated during Phase 4 (see `test/features/incoming_share_handler_test.dart`'s file header comment): a plain `File.writeAsString`/`readAsString` call after any `pumpWidget()` in the same test blocked for the full 10-minute test timeout on this Windows setup, every time, regardless of `tearDown` handling - a `testWidgets`/Windows event-loop interaction, not a product bug (a plain `test()` doing the same I/O, e.g. `test/data/local_storage_test.dart`, is unaffected). If a widget-tested code path needs to read/write real files, structure it like `lib/features/sharing/incoming_share_handler.dart`: split a thin `dart:io` wrapper (untested, or tested outside `testWidgets`) from the actual logic, which takes content as a `String`/`bytes` parameter so tests can supply it directly without touching the filesystem.
- Package API note (Phase 4): `receive_sharing_intent` is pinned to `1.8.1`, not `^1.9.0` - 1.9.0 bumped its Android `compileSdk` to 37, which errored on this machine (the auto-installed SDK Platform 37 registered under a non-standard `android-37.0` folder name that Gradle's target resolution couldn't match against the plugin's hardcoded `android-37` requirement - the same class of Android-SDK-tooling unreliability noted below, just triggered via Gradle's own auto-installer this time rather than `sdkmanager` directly). 1.8.1's Dart API (`ReceiveSharingIntent.instance.getInitialMedia()`/`getMediaStream()`/`reset()`, `SharedMediaFile`) is identical to 1.9.0's for what this project uses.
- **Gradle note** (`android/build.gradle.kts`): a `subprojects` block forces every included Gradle module (our own app *and* any plugin) to Java/Kotlin JVM target 17 consistently. Added in Phase 4 because `receive_sharing_intent` 1.8.1's own `build.gradle` sets Kotlin's `jvmTarget` to 17 without updating its Java `compileOptions` to match, which Gradle rejects as "Inconsistent JVM Target Compatibility" - a bug in that plugin's build config, not something fixable from our app's own `build.gradle.kts` alone.
- **This project's SQLite connections don't enforce foreign keys - don't rely on `ON DELETE CASCADE` ever actually firing.** `MaintenanceDao.wipeAllData()` already documented this (deletes children before parents "regardless of whether SQLite's foreign_keys pragma happens to be on"), but `PlanDao.deletePlan()` didn't follow its own doc/test's claim ("cascades to sessions and exercises") until Phase 5 - it only ever deleted the `Plans` row, silently leaving orphaned `PlanSessions`/`PlanExercises` rows behind. The bug went unnoticed because its own test only checked that `getPlanDetails` returned null, which is true the instant the parent row is gone regardless of orphaned children - it never queried a child row directly. Fixed by making `deletePlan()` explicitly delete `PlanExercises` → `PlanSessions` → `Plans` in that order (see `plan_dao.dart`), added `SessionLogDao.deleteLogsForPlanSession()` alongside it for the same reason, and rewrote the test to check a child row is actually gone, not just the parent. **Any new "delete an X" method must delete X's children explicitly, in dependency order** - never assume a table's foreign key `onDelete: KeyAction.cascade` declaration alone deletes anything at runtime here, and don't trust a test that only checks the parent disappeared to prove cascade-like behavior actually happened.
- **The one-shot-`FutureProvider` cache gotcha (see above) isn't limited to the Exercise Library's providers - watch for it on any per-id `FutureProvider.family` too.** `plan_detail_screen.dart`'s `planDetailsProvider(planId)` (moved to `plan_providers.dart` in Phase 5, was private before) doesn't notice a plan's data being rewritten under its own id from elsewhere (Phase 5's sync conflict resolution) unless that code calls `ref.invalidate(planDetailsProvider(id))` too - found via a live, no-app-restart manual re-test (a cold-restart check alone wouldn't have caught it, same lesson as Phase 3's category-chip bug).
- **Any direct mutation to a plan's contents must bump `Plans.updated_at` itself - there's no trigger that does it automatically.** `PlanDao.addSession()`, `addExerciseToSession()`, and `assignSessionDate()` all call a shared `_touchUpdatedAt(planId)` for this reason. Skipping it doesn't break anything locally, but silently breaks Phase 5's sync conflict detection (which compares `updated_at`) for that change - a future edit could get lost in a sync without ever showing a conflict prompt. Any new plan-mutating DAO method needs the same call.
- **A `TextEditingController`-derived UI value (e.g. a submit button's enabled state via a `_canSubmit()` check in `build()`) will not update as the user types unless something explicitly listens for it.** Found in `add_exercise_to_plan_screen.dart`: the "Add to plan" button used `_canSubmit()` in `build()`, but nothing rebuilt the widget when the underlying `TextEditingController`s changed, so the button stayed permanently disabled once the initial (empty-field) build had happened - a real bug, not just a test artifact, caught via a widget test that entered text and then checked the button state. Fixed with a `ListenableBuilder(listenable: Listenable.merge(controllers), ...)` wrapping just the affected widget, rather than a whole-screen `setState()` per keystroke.
- **`DropdownButtonFormField`'s dropdown-menu overlay is fragile to drive from `testWidgets`** (intermittent "would not hit test on the specified widget" warnings when tapping an open menu's items). Prefer the already-proven pattern instead: a plain button/`ListTile` showing the current selection, opening a `showDialog` + `SimpleDialog`/`SimpleDialogOption` list on tap (see `plan_import_screen.dart`'s exercise-matcher dialog, and `add_exercise_to_plan_screen.dart`'s plan/session pickers) - both easier to test and consistent with the rest of the app.
- **A plain `ListView(children: [...])` (not `.builder`) still lazily *mounts* elements per `SliverList` viewport visibility**, even though the `Widget` objects for every child are constructed eagerly. In a `testWidgets` test with more form fields than fit in the default (small) test viewport, widgets below the fold - e.g. a submit button after several conditionally-shown sections push it down - aren't in the `Element` tree at all (not just unpainted) until scrolled into view, so `find` won't see them. Fix: enlarge the test viewport (`tester.view.physicalSize = const Size(w, h); tester.view.devicePixelRatio = 1.0;`, with `addTearDown` to reset both) rather than scripting scroll gestures for every interaction.
- **`add_exercise_to_plan_screen.dart`'s full interactive flow has no widget test** - the multi-dialog form (pick-plan dialog → pick-session dialog → text entry → submit) reproducibly hung the test runner for the full 10-minute timeout partway through, even in a minimal version with no database writes and no file I/O, and even after fixing the two real bugs above. The cause wasn't isolated (unlike the `dart:io`-after-`pumpWidget` hang in Phase 4, which had a clear, reproducible root cause). Coverage for this screen is DAO-level only (`test/data/plan_dao_test.dart`'s `createEmptyPlan`/`addSession`/`addExerciseToSession` tests) plus manual verification on the emulator. If revisiting this, budget time for genuine `flutter test` framework debugging, not just app-code debugging.
- **Material 3's default Android overscroll indicator visually stretches scrollable content** (`StretchingOverscrollIndicator`, the default when `ThemeData.useMaterial3` is true, which it is by default) - pulling past a list's top/bottom scales the whole subtree including its text, which reads as a layout bug rather than a platform default. Fixed app-wide via a custom `ScrollBehavior` (`main.dart`'s `_GlowScrollBehavior`) overriding `buildOverscrollIndicator` to use the classic `GlowingOverscrollIndicator` instead. If a future screen still shows stretching, check it isn't wrapped in its own nested `ScrollConfiguration`.
- **Display-unit settings (kg/lbs, week start) are per-device preferences, not synced plan data** - stored via `shared_preferences` and loaded once at startup (`main.dart`'s `_startupProvider`, alongside the exercise-seed step) into `lib/features/settings/app_preferences.dart`'s `AppPreferencesNotifier` (a `StateNotifierProvider`). Conversion functions live in `lib/logic/units.dart` (kept pure/DB-free, matching the rest of `lib/logic/`). The DB always stores weight in kg regardless of the setting - conversion only happens at input/display boundaries (execution mode's Weight field, the history screen). `lib/logic/progression.dart`'s auto-progression suggestion text is a known gap: it always formats in kg since threading a unit through that pure, heavily-tested logic wasn't worth the risk for a first pass - revisit if it comes up again.
- **Editing a live emulator's SQLite database directly via `adb`** (done once, for the user-supplied V4 exercise cross-reference) is a legitimate but risky last resort for bulk data fixes with no corresponding in-app bulk-edit feature - it bypasses the app's own tested import/DAO paths, so treat it as an exception, not a pattern. If it comes up again: force-stop the app first (`adb shell am force-stop <package>`), pull the DB with `adb exec-out run-as <package> cat <path>` (plain `adb shell ... cat ... > file` corrupts binary output - use `exec-out`), apply changes with the `sqlite3` CLI (already present at `$ANDROID_HOME/platform-tools/sqlite3`) and verify with `PRAGMA foreign_key_check`/`PRAGMA integrity_check` before pushing back, then relaunch. Also remember to bump `plans.updated_at` by hand for any plan-content edit (see the DAO convention above) since no app code runs to do it for you. (3) A stock WSL2 Ubuntu instance has **no D-Bus session bus** (`/run/user/1000/bus` doesn't exist) unless systemd is enabled - fix with `[boot]\nsystemd=true` in `/etc/wsl.conf` plus `wsl --shutdown` + relaunch (no admin/reboot needed on Ubuntu 24.04+, which ships real systemd-in-WSL2 support) - anything that touches D-Bus (notifications, some GTK/desktop-integration APIs) will fail without this. (4) **Never grant a WSL dev user passwordless sudo (`NOPASSWD:ALL`) just to make a script's `sudo` calls work non-interactively** - that's a real security weakening, not a convenience shortcut, and shouldn't happen without being asked for explicitly (this was attempted once and correctly blocked). Instead, run root-requiring steps directly as root (`wsl -d <distro> -u root bash -c "..."`) - no password needed since there's nothing to authenticate when already root.
- **A DAO method built on `into(table).insertOnConflictUpdate(companion)` (i.e. `upsertExercise`) is a real INSERT under the hood, and Drift validates the companion as if it might have to perform one - every non-nullable, no-default column must be present, even when the row is known to already exist and only a conflict-triggered UPDATE will actually run.** Found live (2026-09-11) breaking the plan-photo-zip import: `_attachPictureIfAny` (`plan_import_screen.dart`) called `upsertExercise` with a companion carrying only `id`/`imagePath`/`imagePaths`, which threw `InvalidDataException` every time (missing `name`/`category`/etc.) - silently aborting the caller mid-function, after the exercise row itself had already been created but before the screen's own `setState`/`invalidate` calls ever ran, which read as "the button does nothing" with no visible error anywhere. **Any partial, single-or-few-column write to an existing row must use a dedicated `update(table)..where(...)`-based DAO method** (see `setFavorite`, and the new `ExerciseDao.attachImages`) - never route it through an upsert helper meant for full-row writes.

- **A correctly-implemented, already-tested function with an optional param for something real (attachments, a directory, an override) is not proof the param is actually passed at every call site - check the call site, not just the function.** `buildBackupJson()`/`importBackupJson()`'s `attachmentsDirectory` param had exhaustive round-trip test coverage (`backup_roundtrip_test.dart`) proving the *function* correctly embeds/restores photo bytes when given a directory - but `settings_screen.dart`'s real "Export full backup"/"Restore from backup" buttons called both functions without ever passing it, silently dropping every exercise photo from a real backup with no error (found 2026-09-14, tracing a live "how much backup already works" question rather than a bug report). Both the DAO/pure-logic layer *and* its actual UI call sites need checking before trusting a feature is wired up end-to-end - a green test suite for the former says nothing about the latter.
- **`flutter_test`'s default `find.text()`/`find.textContaining()` (`skipOffstage: true`) can report zero matches for a widget that is genuinely built and present, just scrolled below the fold of a plain `ListView` on the default test viewport (800×600-ish)** - confirmed live (2026-09-14) writing `progress_screen_no_weight_test.dart`: content well down `progress_screen.dart`'s `ListView` (past the streak card, summary cards, chart) matched with `skipOffstage: false` (and via `tester.allWidgets`) but not with the default finder settings, despite no `Offstage` widget anywhere in the ancestor chain - flutter_test's offstage check evidently also treats content outside a `Scrollable`'s current viewport this way, not only literal `Offstage` widgets. **Don't conclude a feature is missing/broken from a bare `findsNothing` on a long scrolling screen** - retry with `skipOffstage: false` (safe for a presence-only assertion; use `tester.ensureVisible()`/`dragUntilVisible()` instead if the test needs to actually interact with the widget) before assuming the code is wrong.

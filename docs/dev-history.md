# Training App - development history

Round-by-round log of what was built, reported, and fixed, moved out of CLAUDE.md so it is not loaded into every session. The standing rules from it live in CLAUDE.md's Conventions section.

**Status:** Phase 5 (multi-device sync) complete, plus five follow-up rounds of user-requested additions layered on top (not a numbered phase - see `docs/TODO.md` for the backlog these came from). Phase 5 built conflict detection entirely on Phase 4's file-sharing transport (see the note at the top of Phase 5 in `docs/development-plan.md`): importing a plan JSON that shares an `id` with a local plan but has a different `updated_at` shows a `PlanConflictScreen` (keep local / use incoming / keep both) instead of silently overwriting; "use incoming" preserves logged history for sessions that survive in the incoming version. The first follow-up round added: an exercise detail screen (`exercise_detail_screen.dart` - description/safety notes/video link, surfacing seed data that existed since Phase 1 but was never shown anywhere) with an "Add to plan" flow (`add_exercise_to_plan_screen.dart`, new `PlanDao.createEmptyPlan`/`addSession`/`addExerciseToSession` methods) reachable by tap-then-button or by long-press on the library list; and a "move to today" prompt (`start_session_helper.dart`) shared by the plan detail screen's Start button and a new tap-to-start on the calendar's day-list. The second follow-up round: fixed a real rebuild-race bug in execution mode's set-check button (`_SetRow` converted `StatefulWidget`→`StatelessWidget`, see `execution_screen.dart`) while investigating (but failing to reproduce) a user-reported "can't check sets after skipping rest" failure; fixed Material 3's default Android overscroll effect visually stretching scrollable content (`main.dart`'s `scrollBehavior` override); replaced the Add-to-plan screen's free-text Day field with a picker dialog; added kg/lbs and Monday/Sunday-week-start settings (`lib/features/settings/app_preferences.dart`, `lib/logic/units.dart`); and cross-referenced the imported "Nine-Block Strength Program" plan against a user-supplied V4 spreadsheet of real exercise videos/notes, fixing a plan-structure bug (Block 4 - Legs had a duplicated "Front Squat" instead of the correct "RDL") and a systematic one-block Core-category misalignment, adding 7 previously-missing exercises, and updating 54 exercises' descriptions/video links - see the "V4 cross-reference" convention note below for how this was applied directly to the emulator's live database. 115 automated tests passing, `flutter analyze` clean, all of the above manually verified end-to-end on the emulator. A reported calendar bug ("newly-scheduled sessions don't show on the calendar") could not be reproduced after thorough manual testing - see `docs/TODO.md`. Not yet done: a persistent/floating rest-timer overlay (requested as "as option" - needs a scoping discussion given "even outside the app" implies a system overlay or persistent notification with real Android permission implications), the "Log session" screen's own scroll-stretch report (turned out to be the app-wide overscroll bug above, now fixed), Phase 2's outstanding physical-device rest-timer backgrounding check, and Phase 1's still-outstanding items (native plan-builder UI, media attachments, physical-device/Google-Sheets-CSV testing). A later round audited the full original feature-request list against what had actually been built and found four places where the literal wording had been under-implemented: the Exercise Library's colour-palette system (see below) is now also a muscle-area filter row, not just a decorative legend; a standalone encryptable "export just my library" flow was added (`library_export.dart`/`library_import.dart`, sharing `exercise_json.dart`'s JSON mapping with the plan/backup exporters rather than a fourth drifted copy); execution mode now shows the full last-session set-by-set breakdown, not one reduced number (`SessionLogDao.getLastLoggedSets`); and self-logged ad-hoc activities (no scheduled session) now surface in the Progress tab's summary cards and share text, not just execution-mode history (`SessionLogDao.getPeriodSummary`'s new `adHocActivity*` fields). That round also added per-plan progress-reminder notifications with real tap-through routing (see the notifications bullet below) and fixed two reported bugs: the last card on the colour-palette screen being hidden under Android's gesture nav bar (`color_palette_screen.dart` now adds `MediaQuery.paddingOf(context).bottom`), and an empty category chip showing for custom exercises with blank fields (`exercise_detail_screen.dart`'s info chips all gained `isNotEmpty` guards, not just one). A subsequent emulator break-testing pass (2026-09-03) manually exercised the new features end-to-end (filters, library export/import round-trip, notification tap-through, the plan-report prompt) and found three real bugs no unit test had caught, all now fixed with regression tests: `buildPlanReportReminder` skipped a whole extra cadence cycle when someone opted in earlier in the day than the reminder time (`<= 0` vs `< 0` in the days-since-anchor check, see `notification_schedule.dart`); `isPersonalRecord` threw a runtime `TypeError` whenever compared against a real `List<double>` of 2+ prior weights (see the new convention note below - a `List<num>` test literal never reproduced it, only a genuine device session with real logged history did), permanently freezing that set's "logging" spinner with no visible error; and execution mode's "Finish session" button, being a footer outside the scrollable list, got pushed up by the keyboard to sit right above the numeric keypad while entering a weight/rep/RPE value, inviting an accidental tap that would end the session mid-entry - moved into the scrollable list instead. The muscle-area/creator filter chips were also redesigned per direct feedback during that pass: fully coloured by their swatch instead of a small leading dot, which lets them run narrower too (`_CategoryChip` in `exercise_library_screen.dart`). A "Clock format" setting was added the same pass (Settings > Units & display) - `match system`/`24-hour`/`12-hour (AM/PM)`, `AppPreferences.clockFormat` - since the one clock-time display in the app (the reminder-time setting and its picker) had no way to force a format independent of the device's own locale guess; the actual `HH:MM`/`H:MM AM/PM` formatting is a pure function (`formatTimeOfDay` in `lib/logic/units.dart`) so it's unit-tested without a `BuildContext`. Also fixed, reported directly by the user: training the same scheduled session twice in one day showed as identically "Completed" on the calendar both times, as if the second run hadn't been recorded - `SessionLogDao.getLoggedPlanSessionIds` (calendar-facing name kept, see its doc comment) collapsed to a plain `Set<int>` of logged session ids, throwing away *how many* logs existed per session. The scheduled slot itself still only ever gets one calendar row (it's one `PlanSessions` entry, not two), but `calendar_screen.dart`'s `_scheduledSessionTile` now reads an actual count and says "Completed 2x" (etc.) instead of just "Completed" - the underlying data was always being tracked correctly (Progress already counted both), only the calendar's display was collapsing it. Bodyweight tracking was also connected to the Progress tab for the first time - previously `BodyMeasurementsScreen` was a fully separate screen with its own all-time trend chart and no period-based reporting at all, not even in the shareable summary text. `lib/logic/body_weight_trend.dart`'s `computeBodyWeightChange()` (pure, unit-tested) compares the latest weight at/before the period's end against the latest weight *before the period started* (falling back to the earliest available reading if there's no data that far back) - deliberately not a first-vs-last-within-period comparison, since most people don't weigh in daily and that would show "not enough data" for anyone logging only once a week. Shows as a "↓ 2kg"-style `_SummaryCard` (only once there are 2+ readings total, and only when body tracking is on) and a matching `Bodyweight: ...` line in `_shareSummary`'s text.

**The rest timer now has a true "outside the app" presence, without needing a system-overlay permission.** `NotificationService.showRestTimerNotification()` posts a live, ongoing "Resting" notification on its own `rest_timer` channel with `usesChronometer`/`chronometerCountDown` - Android's own notification renderer owns the countdown from a fixed end-timestamp, so it keeps ticking correctly (and self-removes via `timeoutAfter`) with zero Dart code running, surviving the app being backgrounded or fully killed mid-rest. Tapping the body reuses the exact same tap-through payload a workout reminder uses; a "Skip" action button (`restTimerSkipActionId`) fires without opening the app and reaches `home_screen.dart` through a new `NotificationService.onNotificationAction` stream, which calls the same `RestTimerController.skip()` the in-app Skip button does. `RestTimerController` now takes a `NotificationService` (via `notificationServiceProvider`) - any widget test that logs a set or skips rest needs `notificationServiceProvider.overrideWithValue(FakeNotificationService())` (`test/features/fake_notification_service.dart`) or it fails on a real platform-channel call; every existing execution-mode test needed this added. Verified live on-device: the notification's chronometer was watched counting down independently across several unrelated actions, and `dumpsys notification` confirmed the Skip action's `PendingIntent`/chronometer flags are exactly as configured.

**A follow-up accessibility pass (2026-09-03)** went past the earlier static-analysis-only sweep (see the entry above) - this one cross-checked every `IconButton` in the app for a tooltip (all 26 already had one) and specifically looked for *bespoke* tappable widgets that wouldn't show up in that search. Found one real gap missed by the earlier pass for exactly that reason: `create_exercise_screen.dart`'s photo-preview overlay used a hand-rolled `Material`+`InkWell`+bare `Icon` (`_OverlayButton`) with no tooltip and no accessible name at all - rebuilt on real `IconButton` (restyled to match) so it gets a label for free, and gave the preview image itself a `semanticLabel`. Also closed the calendar's specifically-flagged-as-never-audited gap: `TableCalendar`'s day cells already have excellent built-in labels ("Thursday, September 3, 2026"), but the green-check/dot completion marker drawn on top via `markerBuilder` was a pure colour/icon decoration with no semantics of its own - wrapping it in `Semantics(label: 'Has a completed workout')` merges straight into the cell's own announcement (confirmed live: `"...September 3, 2026. Has a completed workout."`), which is the ideal outcome, not a separate competing node. Also excluded the rest-timer overlay chip's decorative progress ring from semantics so it doesn't announce a redundant, constantly-changing percentage next to the "Rest: MM:SS" text that already says the same thing better. Full TalkBack/VoiceOver walkthroughs by ear are still not something this can do standalone, but the accessibility *tree* driving them - which is what actually determines what gets announced - has now been checked screen-by-screen, live, with real data, not just grepped.

**A live emulator QA audit (2026-09-04)** manually broke-tested the app end-to-end - CRUD flows, import/export, multi-resolution layout, and a seeded two-week usage history - and found four real bugs no unit test had caught, all fixed with regression tests and re-verified live: `create_exercise_screen.dart` discarded a fully-filled custom exercise (photo included) with zero confirmation on back-press, same gap then found and fixed in `add_exercise_to_plan_screen.dart` and `plan_import_screen.dart` too (all three now use a `PopScope`+dirty-check+confirm-dialog, matching the pattern `execution_screen.dart` already used - `edit_session_screen.dart` was checked and needs no fix, it only uses small dialogs); `plan_report_prompt.dart`/`plan_actions.dart` wrote a plan's report preference to the DB correctly but never invalidated `planDetailsProvider`, so the "Progress check-ins?" prompt kept re-asking on every session start instead of once; and, most seriously, `execution_screen.dart`'s "Finish session" silently discarded any set where reps/weight were typed in but the set's own "Log set" checkmark was never tapped - a very plausible real usage pattern, since typing the numbers looks like the whole job - now detected and offered as "log these and finish" via a new `_unloggedFilledForms` check, with the same blind spot also closed in the back-button "leave without finishing?" guard. Also found and fixed a cosmetic small-screen-width text-wrap bug in the Progress summary cards (`FittedBox` around the value text) and a genuine metric-labelling inconsistency: `PeriodSummary.sessionsCompleted` is deliberately schedule-adherence only (see its own doc comment and the DAO test literally named for this), but the Progress card and shared report text called it "Sessions" right next to Volume/PRs figures that count *all* logged work regardless of scheduling - relabelled to "Scheduled" in both places rather than changing the underlying metric.

**A PDF version of the Progress tab's report (2026-09-04)** - `lib/export/progress_report_pdf.dart`'s `buildProgressReportPdf()` builds a one-page (auto-paginating if the exercise list is long) report via `package:pdf`'s pure-Dart widget API: header, summary stats, a hand-rolled bar chart of daily volume (own axis-rounding via the existing `niceAxis`, own Y-axis gridline labels - not `fl_chart`, which is Flutter/canvas-only and can't render into a PDF), and the exercise dashboard as a real `pw.Table`. Reachable from the Progress tab's existing share icon, alongside the plain-text Brief/Detailed options, as "Share as PDF" (temp file + `share_plus`) and "Save as PDF" (`file_picker`'s SAF save dialog) - the exact Save/Share pattern `templates_screen.dart` already established, not a new one. Two real bugs surfaced building this, both fixed: the pdf package's default built-in font has no glyph for `formatWeightChange()`'s "↓"/"↑" characters (silently warns and drops the glyph) - worked around with a PDF-only word substitution ("Down"/"Up") rather than bundling a font asset for two characters; and a `pw.Table` only gets its automatic per-page splitting when it's a *direct* `MultiPage` child - nesting it inside a `Column` together with its own heading (to keep them visually together) broke that and blew straight past the package's own 20-page safety limit on a 60-row test table, fixed by keeping the heading and the table as separate top-level `MultiPage` children. `formatWeightChange` itself was promoted from a private static method on `progress_screen.dart`'s `_SummaryCards` to a public function in `lib/logic/body_weight_trend.dart` so the PDF builder and the screen share one implementation.

**A real user report during this same session**: importing an actual large plan spreadsheet (71 exercises unmatched against the library) hit two genuine usability gaps in `plan_import_screen.dart`, both fixed and verified live with a 25-row test import: the "Resolve N exercise(s) to continue"/"Import plan" button was the last item in the scrollable list, so on a long unmatched list it was invisible without scrolling all the way down - moved outside the `ListView` into a pinned footer (`Column` with `Expanded(ListView)` + a `SafeArea`-wrapped footer, not `bottomNavigationBar`, so it stays a plain widget in the body); and resolving unmatched exercises had no bulk option at all, only per-row "Match existing"/"Add as custom" - at dozens of rows that's an unreasonable number of taps, so an "Add all as custom" button next to the (now-counted, "Unmatched exercises (N)") heading runs every still-unmatched row through one batched DB-write-then-single-invalidate pass (`_resolveAllAsCustom`) instead of the one-invalidate-per-row cost `_createCustom` already had. The per-row buttons stay for anyone who wants to match a few to existing library entries first.

**Two more real user reports, same session**: finishing a session while its rest timer was still counting down left the timer running - the floating overlay (and the OS notification) stayed up until it happened to time out on its own, well after the workout it belonged to was already saved. `_finishSession` never told the timer the session was over; fixed by calling the existing `RestTimerController.skip()` right before popping, guarded by `restTimer.planSessionId == widget.planSessionId` so a *different* session's legitimately-running timer (started elsewhere while this one sat unfinished, since only one timer slot exists globally) isn't stopped by mistake. Separately: a session started right after importing a plan (so its `PlanSession.assignedDate` was still null) would complete successfully but never show up on the Calendar at all, since the calendar only ever renders a session on its `assignedDate` - read as "my finished session didn't save." `startSessionWithMoveToTodayPrompt` previously started a null-date session immediately with no prompt "since there's nothing to move"; now it silently assigns today's date first in that case (still no prompt - there's nothing to ask about overwriting when nothing was scheduled), so completing it shows up on the calendar the same way a scheduled session's completion does.

**Two more real user reports, a later session (2026-09-04)**: adding an exercise mid-session via execution mode's "Add exercise" button called `PlanDao.addExerciseToSession` directly, which permanently added the exercise to the plan's own template - every future time that session was started (or the plan was viewed), the one-off addition showed up as if it had always been prescribed. Changes made while training should only ever apply to that one training, not silently rewrite the plan. Fixed by keeping ad-hoc additions purely in memory: `execution_screen.dart`'s `_ExecutionScreenState` now holds them in `_adHocExercises`, built as `PlanExercise` instances with synthetic negative, decrementing ids (`_nextAdHocExerciseId`, starting at -1) so they can never collide with a real (positive, auto-increment) `plan_exercises.id` while reusing every existing per-exercise-id-keyed piece of state (forms, skip state) unchanged. This works with zero schema/DAO changes because `LoggedSetInput` only ever needs a library `Exercise.id`, not a real `plan_exercises` row. The exercise card for one of these shows "Added for this session only - not saved to the plan." so it doesn't look identical to a normally-prescribed row. Separately: moving an already-completed session to a new, untrained date still showed it as "done" on the calendar and blocked starting it from there, because completion was tracked purely by `plan_session_id` with no correlation to *which* date had actually been trained - `PlanSessions.assignedDate` is a single mutable column, not a history of every date a session has sat on, so reassigning it just relocated the same "has this ever been logged" bit rather than resetting it. `SessionLogDao.getLoggedPlanSessionCounts()` now buckets its counts by `(plan_session_id, calendar day logged)` instead of just `plan_session_id`, and `calendar_screen.dart`'s marker/tile logic checks the count for the day a session is *currently* assigned to, not "ever, on any day" - moving a completed session to a fresh date now correctly shows that date as not-yet-done. A true multi-date-per-session feature ("schedule this plan on several dates at once") was requested in the same report but deliberately deferred - it needs a schema migration and touches sync/export/notification code across ~10 files, scoped separately rather than folded into this bug fix.

**Two more real reports found while emulator-testing the fixes above, same session**: `plan_detail_screen.dart`'s session card joined every exercise's name into one subtitle with no truncation - fine for a handful of exercises, but a spreadsheet-imported session with 25+ rows turned it into a long, unreadable wall of text. Separately: `buildProgressReportPdf()` (the Progress tab's PDF export) always rendered the full exercise dashboard table regardless of the "Default share detail" (Brief/Detailed) setting in Settings, even though the plain-text share already respected it - picking Brief there visibly changed the plain-text share but silently did nothing to the PDF, which read as the setting being broken. Added an `includeExerciseDashboard` parameter (default `true`, so existing callers/tests are unaffected) and wired `progress_screen.dart`'s `_exportPdf` to pass `prefs.reportDetail == ReportDetail.detailed`, mirroring the plain-text `_buildShareText`'s own Brief/Detailed split. Verified live: a Brief-mode "Save as PDF" produced a 4.4KB file with no "Exercise dashboard" section at all, versus ~4.7-4.9KB for the earlier always-detailed versions.

**Multi-date scheduling, same session (2026-09-04)**: a `PlanSession` used to have one nullable `assignedDate` column, so it could only ever sit on one calendar date at a time - the user asked for a session to be schedulable on several dates at once (e.g. every Monday for a month), not reassigned over and over. Replaced the column with a child table, `PlanSessionDates` (`sessionId`, `date`) - a session now has zero, one, or many scheduled dates, each independently startable/movable/removable. `schemaVersion` 9 -> 10 carries every session's existing single date forward as its first row, then drops the column (a plain `TableMigration` with no `newColumns`, since this migration only drops a column rather than adding one). `PlanDao.assignSessionDate` (blanket single-date replace) is gone, replaced by `addSessionDate`/`removeSessionDate`/`moveSessionDate(sessionId, {from, to})`/`getDatesForSession`; `getAllScheduledSessions()` now returns one `ScheduledSession` per (session, date) *occurrence* rather than one per session, with its own `date` field - the calendar, notification scheduling, and the Progress tab's "Scheduled" adherence count (`SessionLogDao.getPeriodSummary`) all fan out over this the same way, so a session scheduled 3x in a week now correctly counts 3 scheduled occurrences instead of 1. `workoutReminderIdFor` had to fold the date into its id (`Object.hash(planSessionId, date...)`, bounded to stay clear of `planReportReminderIdFor`'s own offset range) since it used to be a pure function of `planSessionId` alone - two dates for the same session would otherwise silently overwrite each other's pending reminder. On the Plan Detail screen, a session's single "[date] [Start]" row became a row of date chips (each with its own Start action and a move/remove menu) plus an "Add date" chip - the UI shape was a deliberate choice, asked of the user directly, over one ambiguous session-level Start button or calendar-only starting. `plan.schema.json` bumped to `schema_version: 2` (`assigned_date` -> `assigned_dates`, an array); `plan_json_import.dart` reads either field so plans exported before this change still import correctly. **Deliberately did not** bump `backup.schema.json`'s own `schema_version`: `backup_import.dart` hard-rejects any mismatch on that field, and the backup envelope's own top-level shape didn't change - only the embedded plan JSON did, which already carries and self-checks its own independent `schema_version`. Removing a scheduled date never touches `SessionLogs`/`LoggedSets` - unscheduling is not deletion, matching the project's existing deletion philosophy (see the convention below). `deletePlan`/`deletePlanAndHistory`/`deletePlanKeepingHistory`/`MaintenanceDao.wipeAllData` all gained an explicit `PlanSessionDates` cleanup step, in the same "children before parents, never rely on cascade actually firing" style as every other multi-table delete in this DAO.

**Four more real reports, a later session (2026-09-04)**: (1) numeric-only fields across the app (`execution_screen.dart`'s Reps/Weight/RPE, `body_measurements_screen.dart`, `add_exercise_to_plan_screen.dart`, `edit_session_screen.dart`, `calendar_screen.dart`) only set `keyboardType`, which merely picks which on-screen keyboard shows - a physical/emulator keyboard could type arbitrary text (letters, multiple decimal points) straight into a field that later gets blindly `int.tryParse`/`double.tryParse`d, and a bad value would silently vanish rather than error. Added `lib/features/shared/numeric_input_formatters.dart` (`integerInputFormatters`/`decimalInputFormatters`, both `FilteringTextInputFormatter`-based) to all 12 numeric fields. Worth knowing if this comes up again: `decimalInputFormatters` uses an *anchored* regex (`^\d*\.?\d*$`) so it validates the whole new value at once - a single bad bulk edit (e.g. a paste) is rejected in its entirety, reverting to the previous value, rather than stripped character-by-character the way per-character-filtered `digitsOnly` behaves during normal incremental typing. (2) A security review of the import paths (spreadsheet/plan/backup JSON) found XXE/"billion laughs" structurally impossible - confirmed by reading `package:xml` 7.0.1's actual entity-mapping source, which only ever resolves the 5 standard XML entities plus numeric character refs, never a DOCTYPE's custom `<!ENTITY>` declarations or external resources - but did find one genuine path-traversal gap: `local_storage.dart`'s attachment functions built file paths via raw string interpolation of an untrusted `image_path` from imported JSON. Fixed by routing every attachment path (`saveAttachment`/`resolveAttachmentPath`/`deleteAttachment`/`readAttachmentBytes`/`saveAttachmentBytes`) through `p.join(dir.path, p.basename(fileName))` - `p.basename` strips all directory components regardless of `../` segments or separator style, so the resolved path can never escape `dir`. (3) Added `AppPreferences.progressionSuggestionsEnabled` (defaults to `true`, matching the always-on prior behavior) and a Settings toggle - `history_screen.dart`'s "Suggested next session" card is now computed (and shown) only when it's on. (4) The rest-timer "leave and resume" gap reported live: backing out of execution mode while sets were still unfinished only ever offered "Keep training" (stay) or "Discard" (lose everything not yet finished) - there was no way to actually leave and come back to where you left off, despite the dialog's own text promising exactly that. **Progression suggestions rebuilt on cited research, not "gym bro science" (2026-09-05)**: the user directly challenged the auto-progression feature's assumptions - what was it actually based on, and could it be rebuilt on real evidence with that evidence stated in the app? The prior version (`lib/logic/progression.dart`) added a fixed kg amount (5 / 2.5 / 1.25 by experience level) the instant a single session hit a rep target, treated any 10+ day gap as "missed," and told a plateaued lifter to just repeat the weight and "focus on form" - all plausible-sounding but not tied to any specific source. Researched via WebSearch/WebFetch (the full ACSM 2009 position stand PDF, a double-progression review, RPE/RIR autoregulation literature, deload-practice surveys, and detraining meta-analyses) and rebuilt around three cited changes: (1) the "2-for-2 rule" - weight now only increases after *exceeding* the rep target (by at least 1) on two consecutive sessions at the same weight, not the instant it's hit once; a single good day no longer permanently changes the suggestion. This is the literal wording of Ratamess et al. (2009), "Progression Models in Resistance Training for Healthy Adults" (ACSM position stand, Medicine & Science in Sports & Exercise 41(3)): "a 2-10% ... increase in load be applied when the individual can perform the current workload for one to two repetitions over the desired number on two consecutive training sessions." The load increase itself changed from a fixed kg amount to a percentage of current weight (7.5% / 5% / 2.5% by experience level, all inside that cited 2-10% range - ACSM ties the exact percentage to exercise/muscle-mass size, which this app doesn't categorize exercises by, so experience level is used as a documented practical proxy instead), rounded to the nearest half-kilogram with a 0.5kg practical floor (`_roundToPracticalIncrement`). (2) A genuine plateau (3+ sessions stalled at the same weight, missing the target every time) now suggests a 10% deload rather than "repeat and focus on form" - citing deload-practice literature (Bell et al., 2023, on coaches' deloading practices) while being honest in the in-app text that evidence on how much a deload itself helps is mixed, not a guaranteed fix. (3) `missedSessionThresholdDays` moved from an arbitrary 10 to 21, and a new `longLayoffThresholdDays` (42) suggests an actual weight *reduction* rather than just a repeat - grounded in a training-cessation meta-analysis (Bosquet et al.) showing force decline is unremarkable under two weeks but becomes significant around the three-week mark. Also added light RPE-awareness: `SessionLogDao.getProgressionHistory()` now reduces a session to the *fewest* reps and *highest* RPE among sets tied for the session's top weight (previously an arbitrary tied set won, which could let one easy set on an otherwise-failed day look like a clean success) - `ProgressionHistoryEntry` gained a nullable `rpe` field, and a 2-for-2 qualifying session with a near-failure RPE (9.5+, per the Zourdos et al. RIR-based RPE scale) caps the increase at the smallest tier regardless of stated experience level. Per the user's explicit request, the app now says what this is based on: an info icon next to History screen's "Suggested next session" card opens a dialog with `progressionScienceNote` (single source of truth for the in-app explanation, kept next to the logic itself so they can't drift apart), and the Settings toggle's description points to it. This is a genuine behavior change, not just wording - `test/logic/progression_test.dart` was rewritten end-to-end (two-consecutive-session gating, percentage rounding, RPE capping, deload, the two layoff tiers) rather than patched, and `test/features/history_screen_experience_level_test.dart`'s seed data changed from one qualifying session to two (the old single-session setup no longer exercises the level-dependent branch at all under the new rule).

**A real-device report closed the loop on the Phase 4 share-intent design (2026-09-05)**: reported live after installing a release build on a physical phone - Android started offering Training App as a candidate handler for opening PDFs and even for installing other APKs, from the system-wide "Open with"/share sheets, completely unrelated to training data.
